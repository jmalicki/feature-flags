# Parallel copies, not percentages, carry data changes

Engineering organizations do apply progressive delivery to data, but the unit that gets ramped is a *copy* of the data or a *model*, not a percentage of rows. For the first scenario (two versions of a column or table, with a flag choosing which is read or written), a seven-step sequence is documented in first person by Stripe, Notion, Slack, Discord, Uber, LinkedIn, Figma, GitHub and the small ledger company Noah: expand the schema, keep both copies populated, backfill, compare reads while still returning the old answer, switch reads by flag or percentage, switch the authoritative write, then delete the old copy. For the second scenario (an upstream table with about ten derived tables between it and a feature store, and two models trained on two schemas), every link is documented by somebody (LinkedIn's versioned views, Airbnb's hashed dataset versions, Netflix's write-audit-publish, Chronon's `_v2` feature rule, Uber's shadow models, Booking.com's three-arm model experiment), but **no organization has published the whole chain run as one progressive release**, and nobody has published an A/B test whose arms were served from two live data models. The price is time and backfill rather than storage: dual-running lasts from days (Discord's nine-day copy) to years (Slack's three-year Vitess programme), and each new derived-table or feature version is useless until its history is recomputed. The approach breaks in known places, with numbers: a final rename caused a 2-hour-50-minute GitHub outage, a backfill nearly overwrote 13.5 million newer documents at Aircall, a boolean flag gave Noah's services conflicting views of which ledger was live, and silent upstream data changes have degraded models for 45 days (Uber) to six months (Google Play). Two things from code delivery do not carry over: percentage exposure of a table, and cheap undo of whatever downstream tables, features, trained models and payment decisions have already consumed the change. Bank regulators (SR 26-2, PRA SS1/23) ask for validation before use and for challenger and before/after comparison, which shadow runs supply, but neither prescribes traffic splitting.

## Seven published steps run two column versions side by side

The method is twenty years old and has not changed in substance. Ambler and Sadalage's *Refactoring Databases* (2006) defines a "transition period" in which old and new schema are both supported, kept equal by triggers it calls "database scaffolding code", with the old column given a removal date; it warns that "**Typical transition periods last for several quarters, if not years**" when several applications share a database ([Red Gate excerpt](https://www.red-gate.com/simple-talk/databases/sql-server/database-administration-sql-server/refactoring-databases-the-process/)). Ambler's own site adds that a single application owning its database does not need the transition period and can change schema and code together ([agiledata.org](https://agiledata.org/essays/databaserefactoring.html)). Sadalage and Fowler call the same state a transition phase, "a period of time when the database supports both the old access pattern and the new ones simultaneously", and estimate it at "a couple of months" to "years" ([Evolutionary Database Design](https://martinfowler.com/articles/evodb.html)); Danilo Sato named the three phases expand, migrate, contract and noted that canary and blue-green releases are applications of the same pattern ([ParallelChange](https://martinfowler.com/bliki/ParallelChange.html)). What changed after 2015 is the reason for coexistence: rolling deploys and gradual ramps mean old and new code always run together inside one application, so the transition period shrinks from quarters to hours or weeks when one team owns every reader. That last point is the researchers' inference from comparing the 2006 sources with the later case studies, not a claim any one source makes.

The reader's phrase "possibly after refactoring the schema first" corresponds to a real fork in the evidence. There are two layers that are easy to merge. The **physical layer** (rewriting a large table without locking it) is solved by tools: gh-ost, which GitHub uses to run schema changes "multiple times per day" by tailing the binary log instead of using triggers ([GitHub](https://github.blog/news-insights/company-news/gh-ost-github-s-online-migration-tool-for-mysql/)); Facebook's OnlineSchemaChange ([OSC wiki](https://github.com/facebookincubator/OnlineSchemaChange/wiki/How-OSC-works)); Shopify's LHM; Square's Shift service, which runs "thousands of databases migrations every month" ([Square](https://developer.squareup.com/blog/shift-safe-and-easy-database-migrations/)); Vitess VReplication; and Postgres `ADD CONSTRAINT ... NOT VALID`, which skips the full-table scan and validates existing rows later ([PostgreSQL docs](https://www.postgresql.org/docs/current/sql-altertable.html)). These tools leave applications seeing one schema. The **logical layer** (old and new code both correct against the same data) is solved by procedure. Figma is the clearest example of refactoring first: it separated "logical sharding" from "physical sharding", created Postgres views per shard on the still-unsharded database, routed reads and writes through them with feature flags and percentage rollout, and could roll back "within seconds by just rerouting traffic back to the main table", before any data physically moved ([Figma](https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/)). GitHub similarly found and removed cross-domain joins with query and transaction linters, shipping each rewrite "behind Scientist experiments that execute both the old and new implementations for a subset of requests", before moving tables ([GitHub](https://github.blog/engineering/infrastructure/partitioning-githubs-relational-databases-scale/)).

The table gives the recipe. "Documented" means at least one named organization describes doing the step in first person; "vendor" means the main source sells the tool; "inference" means the step is the researchers' assembly.

| --- | --- | --- | --- |

| 2. | 5. Switch reads by flag or percentage | Return the new copy for a growing share | Figma percentage rollout; Aircall 5%, 25%, 50%, 100% per cluster ([Aircall](https://aircall.io/en-gb/blog/tech-team-stories/elasticsearch-to-opensearch/)); Uber validation percentage adjustable "within seconds" ([Uber](https://www.uber.com/blog/schemaless-rewrite/)); LinkedIn per customer; LaunchDarkly "shadow" and "live" stages ([LaunchDarkly](https://launchdarkly.com/docs/guides/flags/migrations)) | Documented; LaunchDarkly is vendor |
| 6. | 7. Contract | Stop writing old, delete old column after release spacing | GitLab three-release drop with `remove_after` date; Stripe made the old accessor raise a hard error to find stragglers; Uber kept DynamoDB about a month after writes stopped ([Uber](https://www.uber.com/blog/migrating-from-dynamodb-to-ledgerstore/)) | Documented |

Stripe's 2017 post is still the single best narrative of steps 1 to 7 for a payments company: "hundreds of millions" of Subscription objects moved out of an array on Customer records with no maintenance window, reads compared through Scientist with an alert on any mismatch, and switched only "After we verified that everything matched up" ([Stripe](https://stripe.com/blog/online-migrations)). It is also incomplete in ways the article should respect: it gives **no durations, no mismatch counts, no ramp percentages, and does not say how the read switch was gated** or how rollback worked after phase 3. Two rules emerge across the accounts. Reads are easy to gate and compare per request, writes are not: GitHub says "we only use Scientist on read operations" because a candidate that writes to the same database is "dangerous and incorrect" ([GitHub Scientist](https://github.blog/developer-skills/application-development/scientist/)), and Uber validated read endpoints by double execution but covered writes with tests and then moved write traffic by percentage ([Uber](https://www.uber.com/blog/schemaless-rewrite/)). And a flag that selects the *authoritative* store needs stronger consistency than an ordinary feature flag: Noah's boolean flags were evaluated inconsistently because of caching and deployment, so "different parts of the system occasionally had conflicting views of which ledger was active" ([Noah](https://noah.com/blog/zero-downtime-migration-of-noahs-internal-ledger)). Everyone else used a routing token (Stripe DocDB's "versioned gating"), a short write pause (GitHub, Shopify), or a scheduled window (Notion, LinkedIn).

GitLab's documentation is the most detailed public statement of the "schema works with version N and N-1" rule, and it shows the price. Dropping a column takes three releases (ignore it, drop it, remove the ignore rule) because Rails caches columns at boot and "dropping a column is a destructive operation that can't be rolled back easily"; renaming a table goes through a compatibility view; and under canary deploys "it is possible that the system runs in this state for a significant amount of time" ([GitLab](https://docs.gitlab.com/development/database/avoiding_downtime_in_migrations/), [GitLab rename tables](https://docs.gitlab.com/development/database/rename_database_tables/)). GitLab's procedures are driven by release order, not by a per-user flag. The vendor tool pgroll goes furthest toward literally "two versions of a column side by side": it serves each schema version as a Postgres schema of views and keeps old and new physical columns in sync with triggers for the whole migration, so a client chooses a version with `search_path` ([pgroll](https://github.com/xataio/pgroll)). No independent production account of pgroll at scale was found, and version selection is per connection, which maps to "old app version versus new app version" rather than to a per-user flag.

## The ten-table chain is documented link by link, never whole

The second scenario is where the public record thins out. The researchers' honest summary is: **each link of the chain is documented by its implementers; the whole chain, run as one progressive release, is not.** Published end-to-end stories cluster at the two ends. At the source, companies forbid breaking change: LinkedIn's 2012 pipeline allowed only additive Avro changes ("new fields can be added, but must have a default value") with a failed compatibility check producing "a fatal error" ([LinkedIn 2012](http://sites.computer.org/debull/A12june/pipeline.pdf)), and Shopify says "Breaking schema changes are extremely disruptive for our downstream consumers, so we do our best as a company to avoid them whenever possible" ([Shopify](https://shopify.engineering/capturing-every-change-shopify-sharded-monolith)). At the model, companies shadow, canary and A/B test. The middle, the parallel intermediate tables, appears in first person only implicitly. The researchers' explanation, which is inference, is that large firms avoid the scenario by forbidding breaking source changes and by logging served features, so a "new schema" reaches a model as new columns in a log rather than as a second pipeline; the parallel-pipeline design is what a warehouse-centric team needs when neither holds, which describes many banks.

The design principle that makes steps 8 to 10 safe is stated directly by the feature platforms: the unit is "one model, one named feature set." Feast's 2026 design note uses the reader's scenario as its motivating case ("model A uses v1 features, model B uses v2 features") and rejects a shared table with a version column because "a model trained against v1 of a feature must retrieve v1 rows, not v2 rows that happen to occupy the same table" ([Feast](https://feast.dev/blog/feature-view-versioning)). A feature flag or experiment therefore selects a *model*, and the feature version follows from the model, never from the flag directly; Hopsworks puts it as "versioning the model alone is not enough" ([Hopsworks](https://docs.hopsworks.ai/latest/concepts/fs/feature_group/versioning/)). Booking.com's design is the one to cite for a fair model comparison: the control group "invokes and uses the output from model 1, the current baseline, and also works as a safety net", and in both treatment arms "the outputs from both models are required", which removes latency as a confound and lets analysis focus on requests where the models disagree ([Booking](https://doi.org/10.1145/3292500.3330744)). Computing both models in both treatment arms doubles inference and feature-fetch cost there; that is the price of fairness.

An alternative to the backfilled v2 chain exists and is the one large firms often choose: log features at serving time and train on the logs. Google's Rules of ML recommends it (Rule #29) and reports that "YouTube home page switched to logging features at serving time with significant quality improvements" ([Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)); Uber Eats built a new training table from logged features beside the old ETL table. The cost is calendar time: Chronon's README warns "It might take a long to accumulate enough data to train the model" ([Chronon](https://raw.githubusercontent.com/airbnb/chronon/main/README.md)), and Netflix, which logs raw facts and regenerates features, says regeneration "takes hours compared to weeks taken by the feature logging" ([Netflix, mirror copy](https://noise.getoto.net/2022/04/26/evolution-of-ml-fact-store/)).

| Slack, MySQL to Vitess | "exactly three years" to move 99% of query load | [Slack](https://slack.engineering/scaling-datastores-at-slack-with-vitess/) |
| Uber Palette metadata rearchitecture (old and new behind a kill switch) | More than a year | [Uber](https://www.uber.com/blog/palette-meta-store-journey/) (tool-extracted) |
| Staged ML deployments generally | "could take several months" (interview study, 18 engineers) | [Shankar et al.](https://arxiv.org/pdf/2209.09125) |

Runtime costs are documented qualitatively. Notion's dark reads "increased API latency"; Uber's double execution doubled storage requests and had to be sampled; Uber Mezzanine used "a probabilistic approach to control the additional load" because the old database was already overloaded; and Stripe called converting every write path "arguably the most challenging part of the migration" across "thousands of lines of code across multiple services". Uber Eats' serve-time feature logging ran about 1.7 PB/day before compression (tool-extracted, [Uber](https://www.uber.com/blog/taming-ml-firehose/)).

In the analytical chain the dominant cost is not duplicate storage but **backfill**, because a v2 table or feature is useless until its history is recomputed, and for chained tables the recompute is sequential. Airbnb admitted that "backfills often could not catch up with user changes, especially when updates affect many datasets", so a fast-changing dataset "could end up in backfill mode forever"; its fix was a shared staging environment that backfills pending changes before they merge ([Airbnb](https://medium.com/airbnb-engineering/airbnb-metric-computation-with-minerva-part-2-9afe6695b486)). Netflix reports that late-data lookback windows cost "almost X times more" (X the window in days), and that rebuilding a 14-day-window pipeline incrementally used about 10% of the resources ([Netflix](https://netflixtechblog.com/incremental-processing-using-netflix-maestro-and-apache-iceberg-b8ba072ddeeb)). Tecton files in-place feature redefinition under cost: re-materialization "incurs cost and downtime" ([Tecton](https://docs.tecton.ai/docs/manage-costs/suppress-recreates)). DoorDash's embedding pipelines ran "about 10 to 12 hours every day", so one change took a day to propagate ([InfoQ](https://www.infoq.com/presentations/fabricator-ml)). dbt's own documentation names the trade-off between migrating consumers and "the cost (and clutter) of materializing multiple versions" and says sunsetting versions "requires real work, and likely significant coordination across teams" ([dbt](https://docs.getdbt.com/docs/mesh/govern/model-versions)). The originators of versioned signals priced it in 2015: "Versioning carries its own costs, however, such as potential staleness and the cost to maintain multiple versions of the same signal over time" ([Sculley et al.](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)). Old versions accumulate because removal is gated by model references and done by hand: Feast's design records "No mechanism to prune old versions" ([Feast ADR-0008](https://docs.feast.dev/project/adr/adr-0008-feature-view-versioning)), the data equivalent of the flag debt the essay already discusses.

## Where it breaks: outages, drift, one-way switches and silent months

The operational-database failures come from the migration machinery itself. GitHub reported that trigger-based tools before gh-ost "would consistently cause MySQL outage" and that "the master is brought down by the load of the triggers" even while row copy was throttled ([GitHub](https://github.blog/news-insights/company-news/gh-ost-github-s-online-migration-tool-for-mysql/)). On 27 November 2021, the final rename step of a schema migration on a large table put a significant portion of GitHub's read replicas into a semaphore deadlock and crash recovery, and **core services were unavailable for 2 hours 50 minutes**; GitHub paused schema migrations afterward ([GitHub](https://github.blog/news-insights/company-news/github-availability-report-november-2021/)). GoCardless "took around 15 seconds of unexpected API downtime during a planned database migration" when a foreign-key lock queued behind a long-running read, though the same migration took a few hundred milliseconds against a backup ([GoCardless](https://gocardless.com/blog/zero-downtime-postgres-migrations-the-hard-parts/)). Shopify showed by experiment that an LHM migration can silently lose rows for one combination of NOT NULL, default, unique index and strict mode ([Shopify](https://shopify.engineering/add-not-null-colums-to-database)). Dual-written copies drift: Notion rejected application dual writes because "any issue with either write can quickly lead to inconsistencies between databases"; LinkedIn said "It is extremely hard to implement dual write with distributed transactions between two systems" and ran four separate verification loops; and Aircall (June 2026) found that a default reindex backfill "would have silently overwritten 13.5M newer documents with stale copies" of about 850 million while reporting zero failures, caught only by a pre-flight count check ([Aircall](https://aircall.io/en-gb/blog/tech-team-stories/elasticsearch-to-opensearch/)). Several switches were not online at all: Notion's five-minute window, LinkedIn's per-customer unavailability window on Sunday mornings, Figma's ten seconds of partial availability, Stripe DocDB's under-two-second rejection of requests. "Zero downtime" in these accounts usually means seconds of rejected or retried writes. And some migrations are one-way: LinkedIn's old and new Recruiter models were not one-to-one, so "it is not practical to go back and forth between the two systems."

The researchers distil four situations in which the operational pattern stops working or stops being cheap, an inference supported by these cases: the two models are not mutually convertible, so there is no rollback after the switch (LinkedIn); the old database is too loaded to bear triggers, backfill or comparison reads (Notion, Uber, GitHub before gh-ost); writes cannot be compared or replayed safely, so only reads get shadow-tested (GitHub, Uber); and the authoritative-store switch needs atomicity that ordinary flags do not give (Noah).

The analytical and ML failures are different in kind: the change is legal at its origin, passes type checks, and degrades rather than breaks the model, so a human notices weeks or months later. Uber's fares dataset lost a fare component because "an app experiment that started logging fares differently"; it was "detected after 45 days manually by one of the data scientists" and Uber estimates such incidents at millions of dollars; partial-data incidents took five times longer to detect than ETL or infrastructure failures ([Uber D3](https://www.uber.com/blog/d3-an-automated-system-to-detect-data-drifts/)). The upstream change there was itself a flagged experiment whose data side effect was not carried through the chain, which is directly relevant to the article. Google Play "once had a table that was stale for 6 months, and refreshing the table alone gave a boost of 2% in install rate" ([Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)). A Google video-recommendation migration silently dropped features because a backend stored them in a different format; with validation "The total time to diagnose and fix the problem was two days, whereas similar issues have taken months to resolve" ([Breck et al.](https://mlsys.org/Conferences/2019/doc/2019/167.pdf)). Google Research's data-cascades study found drift-type cascades taking "up to 2-3 years" to manifest ([Google Research](https://research.google/blog/data-cascades-in-machine-learning/)). Lyft reports that bad Hive data "caused tainted experimentation metrics, inaccurate machine learning features, and flawed executive dashboards" ([Lyft](https://eng.lyft.com/from-big-data-to-better-data-ensuring-data-quality-with-verity-a996b49343f6)). Structural gates do not catch these: dbt lists "Changing logic behind a metric", granularity and filters as changes that "might be breaking depending on your business logic", which its contracts cannot detect ([dbt](https://docs.getdbt.com/best-practices/how-we-mesh/mesh-6-coordinate-versions)), and LinkedIn's canonical example of a semantic change is a time field moving from seconds to milliseconds ([LinkedIn](https://engineering.linkedin.com/blog/2017/11/dali-views--functions-as-a-service-for-big-data)). Model-level canaries do not catch them either, because the model is not what changed.

Feature stores add their own limits. Chronon states that "While 100% consistency is desirable, it is not always possible" for streaming features. Tecton will not apply in place changes that "would invalidate the checkpoint" of a windowed stream aggregate. Embeddings must be fully recomputed and cannot mix versions (Hopsworks' own example of a breaking change). Feast's 2026 multi-version serving is experimental and "Version-qualified reads are only on SQLite initially" ([Feast ADR-0008](https://docs.feast.dev/project/adr/adr-0008-feature-view-versioning)); Google's managed product "only supports the version 0 for features" ([Google Cloud](https://cloud.google.com/vertex-ai/docs/featurestore/latest/overview)); and SageMaker features, once added, "you cannot remove" ([AWS](https://docs.aws.amazon.com/sagemaker/latest/dg/feature-store-update-feature-group.html)). Uber's 2021 feature-metadata incident (tool-extracted) took several hours to resolve, and rollbacks were prolonged because one change touched hundreds of feature groups ([Uber](https://www.uber.com/blog/palette-meta-store-journey/)).

The model end has statistical limits. Across "23 comparisons (46 models)" at Booking.com, offline gain correlated with business gain at Pearson -0.1 (90% CI -0.45 to 0.27), so "Offline model performance metrics are only a health check"; as models converge the "disagreement rate goes down", and power with it; review labels arrive "months later" ([Booking](https://doi.org/10.1145/3292500.3330744)). Adyen says "in mature product orgs, AB tests often come back flat or insignificant" ([Adyen](https://www.adyen.com/knowledge-hub/the-ai-behind-uplift)). Adoption is slow even at leaders: Uber reached shadow coverage of "over 75% of critical online use cases" only in 2025 (tool-extracted, [Uber](https://www.uber.com/blog/raising-the-bar-on-ml-model-deployment-safety/)). No first-party post-mortem of a staged model rollout going wrong was found.

## Percentage ramps and cheap undo do not survive the move to data

The progressive-delivery toolkit translates to data piece by piece, but two of its load-bearing properties do not. The table summarizes; everything in the right-hand column is supported by the sources above, and the framing is the researchers' synthesis.

| Code technique | Data equivalent | What carries over | What does not |
| --- | --- | --- | --- |
| Dark launch | Dual-write, shadow table, write-audit-publish, model shadow | Run the new path on real inputs with no consumer seeing it | Writes cannot be run twice safely; only reads get per-request comparison |
| Feature flag | Flag or routing token choosing which copy is read, or which model serves | Instant switch of the read path (Figma: seconds) | A flag choosing the authoritative store needs atomic consistency (Noah); the flag does not remove the need for the expanded schema and backfill |
| Percentage ramp | Percentage of reads, of dual-written objects, of customers, of model traffic | Works for operational reads and model traffic (Aircall, Figma, Stripe, Uber) | No percentage exposure for a derived table: 5% of rows on a new derivation is not a coherent table. Analytical ramps go by consumer or job batch (Meta, dbt, Minerva) |
| Automated health gate | Contracts, data tests, row-count and checksum diff, drift checks, model blessing | Pre-publish gate is the main safety mechanism | Structural checks miss semantic change; business-metric auto-rollback not documented |
| Rollback | Snapshot pointer move (Iceberg, Delta RESTORE, Snowflake SWAP), model artifact revert | One table or one model reverts in seconds | Downstream tables, features and trained models already built stay wrong until recomputed; Delta warns RESTORE re-emits rows to streaming readers, "processing them may result in duplicate data", and VACUUM's 7-day default bounds how far back you can go ([Delta](https://docs.delta.io/latest/delta-utility.html)); Meta notes CDC carries bad landed data forward |
| A/B test | Experiment assigning models | Mature ML teams already select models through the general experimentation platform (Booking, LinkedIn, Adyen, Meta) | Not documented across two live data models; decisions already taken (blocked payments) cannot be undone |

The defensible statement for the article is that for data, rollback is per table and fast, undo of downstream effects is a backfill, and the main safety mechanism is therefore the pre-publish gate plus versioned coexistence, not post-release ramping. Write-audit-publish exists precisely to avoid "the loss of trust that can occur if processed data is made available and then retrospectively withdrawn or fixed" ([lakeFS](https://lakefs.io/blog/data-engineering-patterns-write-audit-publish/)). For model decisions in payments the irreversibility is sharper: Stripe says blocked payments "are blocked, and so we can't know what their outcomes would have been" ([Stripe](https://stripe.com/guides/primer-on-machine-learning-for-fraud-protection)), and Adyen that "once we apply a decision on a transaction (e.g. block it for fraud likelihood) we do not have access to the outcome if we wouldn't have acted on it" ([Adyen](https://www.adyen.com/knowledge-hub/the-ai-behind-uplift)). Reverting the model restores behavior; wrongly declined customers, approved fraud and a training set labeled only where the bad model let outcomes be seen all persist. None of these limits argues for a release train, which has the same irreversibility with larger exposure; they argue for longer shadow, randomized control or holdout slices, and explicit cost budgets for them. That is the researchers' inference, consistent with the essay's thesis.

## Payments firms and bank regulators supply fragments, not the chain

The financial-services record is the strongest at the operational end. Stripe's 2017 Subscriptions migration and its 2024 document-database platform (5 million queries per second, 2,000+ shards, 1.5 petabytes moved in 2023, a traffic switch that "takes less than two seconds", and replication kept bidirectional so that traffic can be reverted to the source) are first-party and read in full ([Stripe 2017](https://stripe.com/blog/online-migrations), [Stripe 2024](https://stripe.com/blog/how-stripes-document-databases-supported-99.999-uptime-with-zero-downtime-data-migrations)). Uber's payments ledger migration supplies the only quantitative argument about how long shadow confidence takes, and the warning that "live shadow validation can't give strong guarantees about our corpus of rarely-accessed historical data", which forced an offline comparison of 760 billion records in a single job ([Uber](https://www.uber.com/blog/migrating-from-dynamodb-to-ledgerstore/)); for a core-banking system with lower request rates, reaching the same confidence by shadowing takes longer, not shorter. Noah's QLDB-to-Aurora ledger move is the clearest small-company account of feature-flagged dual ledgers and their failure ([Noah](https://noah.com/blog/zero-downtime-migration-of-noahs-internal-ledger)). GoCardless supplies the lock-queue outage and, through Andrew Jones, the data-contracts rationale; six months in, contracts powered about 50% of asynchronous inter-service events but had "not yet seen the same kind of adoption for data primarily produced for the data teams" ([GoCardless](https://medium.com/gocardless-tech/data-contracts-at-gocardless-6-months-on-bbf24a37206e)). PayPal published its data-contract template, now the Open Data Contract Standard, without describing how consumers migrate between versions ([PayPal](https://github.com/paypal/data-contract-template)).

At the ML end, the banks and payments firms describe the stages without numbers. Monzo exports "a versioned snapshot" of each training dataset, uses "data validation queries implemented as ingestion preconditions", and says "we use shadow mode deployments extensively" ([Monzo](https://monzo.com/blog/2022/04/26/monzos-machine-learning-stack)); its former ML lead defines shadow as systems that "log data about all of their decisions, and then return a default value as if they were off", and names "low-volume/high-impact traffic (as is the case in fraud monitoring)" and regulatory guidance as reasons A/B testing may be impeded ([Lathia](https://nlathia.github.io/2020/07/Shadow-mode-deployments.html)). Nubank runs fraud models in shadow, where the model "processes real data but doesn't affect customer-facing decisions", against a 700ms PIX latency budget ([Nubank](https://building.nu.com/practices-to-scale-machine-learning-operations/)), and advises "Deploy the model in shadow mode as early as possible" ([Nubank](https://building.nu.com/de-risking-real-time-ml-projects-addressing-common-failure-modes/)). Adyen's lifecycle is ghost, challenger, principal, retired; its control group keeps a "market baseline" (blocking known-stolen cards and similar) so uplift is "lower, but more honest", and it reports off-policy estimates with "+80%" correlation to actual A/B tests, saving about 20 weeks a year of flat tests ([Adyen](https://www.adyen.com/knowledge-hub/the-ai-behind-uplift)). Stripe's Shepherd feature platform built monitoring on Chronon's online-offline consistency for a SEPA fraud model with "over 200 features" that "blocks tens of millions of dollars of additional fraud a year" ([Stripe](https://stripe.com/blog/shepherd-how-stripe-adapted-chronon-to-scale-ml-feature-development)), but neither Shepherd nor the Radar architecture post mentions shadowing, backfilling or ramping a new feature. The one regulated credit-data failure with primary documentation is Equifax's 2022 "coding issue within a legacy, on-premise server environment", which ran "between March 17 and April 6" and shifted scores by 25 points or more for "less than 300,000 consumers" ([Equifax](https://www.equifax.com/newsroom/all-news/-/story/equifax-statement-on-recent-coding-issue/)); the statement does not say whether it was an input or schema change. No bank or payments firm has published the complete chain, and no regulator enforcement action citing an ML input or schema change was found.

Regulation asks for comparison evidence, not for a deployment mechanism. **SR 26-2** (17 April 2026, Federal Reserve with OCC and FDIC) "supersedes and replaces SR letter 11-7" and is "expected to be most relevant to banking organizations with over $30 billion in total assets" ([SR 26-2](https://www.federalreserve.gov/supervisionreg/srletters/SR2602.htm)). Its attachment says "Validation generally occurs prior to a model's first use", allows earlier use for urgent need with "placing limits on model use or more closely monitoring its performance", requires outcomes analysis that "compares model outputs to corresponding real-world outcomes", and takes generative and agentic AI out of scope; a search of the text found no occurrence of "parallel", "champion" or "challenger" ([SR 26-2 attachment](https://www.federalreserve.gov/supervisionreg/srletters/SR2602a1.pdf)). **PRA SS1/23** (in force 17 May 2024) is more specific: development testing should compare output "with the output of available challenger models" where practicable; material changes, including changes over time in dynamic models, require before-and-after comparison against outcomes, which the PRA calls "parallel outcomes analysis"; monitoring includes benchmarking, sensitivity testing and analysis of overrides; and a decommissioned model "may be used as a challenger model itself" ([PRA SS1/23](https://www.bankofengland.co.uk/-/media/boe/files/prudential-regulation/supervisory-statement/2023/ss123.pdf)). The EBA's 2023 report describes ML challenger models as offline validation tools ([EBA](https://www.eba.europa.eu/sites/default/files/document_library/Publications/Reports/2023/1061483/Follow-up%20report%20on%20machine%20learning%20for%20IRB%20models.pdf)). Neither text prescribes production A/B tests or traffic splitting; "champion/challenger" as a traffic split is implementer language. The researchers' inference is that a shadow run is the stage that fits before validation sign-off, because it takes no decisions, while even a small live challenger slice counts as use and needs prior validation or explicit limits; and that shadow plus a controlled split generates exactly the before/after and challenger evidence the PRA asks for. No regulator says this. SR 11-7's own wording could not be retrieved, so the article should not characterize what it said about parallel runs.

## Conclusion

The reader's objection is half right. Data changes can be shipped with dark launches, flags, comparison and staged switches, and the companies that publish about it (several of them in payments) have done so for a decade; but what gets staged is a parallel copy or a parallel model, and the expensive parts (expanded schema, backfill, reconciliation, reverse sync) do not shrink because a flag sits in front of them. For the article, the useful reframing is that a release train and a data migration share a property that code rollouts lack: effects that leave the system cannot be recalled. Progressive delivery's answer for data is therefore not "ramp and roll back" but "keep both versions alive, prove equivalence or improvement before consumers depend on the new one, and switch with a reverse path in hand." That is still an argument against the train, because the train ships the same irreversible change to everyone at once with less evidence.

The evidence also points to where the article should be modest. The full ten-table chain into two models under an A/B test is a composition of documented parts, not a documented practice, and the most common way large firms avoid needing it (additive-only source changes and logging served features) deserves equal billing with the parallel-chain recipe. The failure record is more persuasive than the success record: silent upstream changes degraded models for 45 days to six months at firms with strong tooling, and the defence every one of them names (validation on each batch, training-versus-serving comparison, drift detection on tiered datasets) is the same observation capability a staged data rollout requires. For banks, PRA SS1/23's "parallel outcomes analysis" gives the article a regulatory hook that SR 26-2 does not, and a shadow stage before validation sign-off is the natural place to put it.
