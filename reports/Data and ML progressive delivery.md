# Parallel copies, not percentages, carry data changes

Engineering organizations do apply progressive delivery to data, but what gets ramped is a copy of the data, a second stream job or a model, not a percentage of rows. For the first scenario (two versions of a column or table, with a flag choosing which is read or written), Stripe, Notion, Slack, Discord, Uber, LinkedIn, Figma, GitHub and the small ledger company Noah each describe, in the first person, the same seven steps: expand the schema, keep both copies populated, backfill, compare reads while still returning the old answer, switch reads by flag or percentage, switch the authoritative write, then delete the old copy. For the second scenario (an upstream table with about ten derived tables between it and a feature store, and two models trained on two schemas), every link is documented by somebody, but no organization has published the whole chain run as one progressive release, and nobody has published an A/B test whose arms were served from two live data models. For the third scenario (event schemas and stream processors), schema registries enforce "old and new readers coexist" mechanically and fix the order in which producers and consumers upgrade; breaking changes go to a new topic, and Jay Kreps's 2014 procedure (start a second job from the beginning of the log, write to a new output, switch readers, keep the old output for instant revert) is the documented progressive pattern, with Grab's 2026 automated shadow stage the only first-person account of shadowing a stream job. The price is time and backfill rather than storage: dual-running lasts from days to years, each new derived table, feature or stream output is useless until its history is rebuilt, and stream replay is bounded by log retention (Uber keeps only a few days). The approach breaks in known places: a final rename caused a 2-hour-50-minute GitHub outage, a backfill nearly overwrote 13.5 million newer documents at Aircall, a boolean flag gave Noah's services conflicting views of which ledger was live, silent upstream changes degraded models for 45 days (Uber) to six months (Google Play), and stream state often cannot survive a change to keys or stateful operators. Ownership is the other half: contracts, named owners and consumer reviewers are documented at GoCardless, Uber, LinkedIn, Monzo and Nubank, and LinkedIn deliberately put its most shared tables on a committed monthly change cadence. Regulators in the US, UK and continental Europe all require validation before live use and accept or expect parallel comparison before sign-off; continental rules add a regulatory clock for internal-model changes (including a two-month notice for changing an IRB model's data sources), customer rights that apply to every experiment arm, fraud-rate limits that make a bad challenger a regulatory event, and DORA's rule that testing in production is an approved, time-limited exception. No regulator defines or forbids a traffic-split experiment.

## Seven published steps run two column versions side by side

The method is twenty years old and has not changed in substance. Ambler and Sadalage's *Refactoring Databases* (2006) defines a "transition period" in which old and new schema are both supported, kept equal by triggers it calls "database scaffolding code", with the old column given a removal date; it warns that "Typical transition periods last for several quarters, if not years" when several applications share a database ([Red Gate excerpt](https://www.red-gate.com/simple-talk/databases/sql-server/database-administration-sql-server/refactoring-databases-the-process/)). Ambler's own site adds that a single application owning its database does not need the transition period and can change schema and code together ([agiledata.org](https://agiledata.org/essays/databaserefactoring.html)). Sadalage and Fowler call the same state a transition phase, "a period of time when the database supports both the old access pattern and the new ones simultaneously", and estimate it at "a couple of months" to "years" ([Evolutionary Database Design](https://martinfowler.com/articles/evodb.html)); Danilo Sato named the three phases expand, migrate, contract and noted that canary and blue-green releases are applications of the same pattern ([ParallelChange](https://martinfowler.com/bliki/ParallelChange.html)). What changed after 2015 is the reason for coexistence: rolling deploys and gradual ramps mean old and new code always run together inside one application, so the transition period shrinks from quarters to hours or weeks when one team owns every reader. That last point is the researchers' inference from comparing the 2006 sources with the later case studies, not a claim any one source makes.

The reader's phrase "possibly after refactoring the schema first" corresponds to a real fork in the evidence. There are two layers that are easy to merge. The physical layer (rewriting a large table without locking it) is solved by tools: gh-ost, which GitHub uses to run schema changes "multiple times per day" by tailing the binary log instead of using triggers ([GitHub](https://github.blog/news-insights/company-news/gh-ost-github-s-online-migration-tool-for-mysql/)); Facebook's OnlineSchemaChange ([OSC wiki](https://github.com/facebookincubator/OnlineSchemaChange/wiki/How-OSC-works)); Shopify's LHM; Square's Shift service, which runs "thousands of databases migrations every month" ([Square](https://developer.squareup.com/blog/shift-safe-and-easy-database-migrations/)); Vitess VReplication; and Postgres `ADD CONSTRAINT ... NOT VALID`, which skips the full-table scan and validates existing rows later ([PostgreSQL docs](https://www.postgresql.org/docs/current/sql-altertable.html)). These tools leave applications seeing one schema. The logical layer (old and new code both correct against the same data) is solved by procedure. Figma is the clearest example of refactoring first: it separated "logical sharding" from "physical sharding", created Postgres views per shard on the still-unsharded database, routed reads and writes through them with feature flags and percentage rollout, and could roll back "within seconds by just rerouting traffic back to the main table", before any data physically moved ([Figma](https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/)). GitHub similarly found and removed cross-domain joins with query and transaction linters, shipping each rewrite "behind Scientist experiments that execute both the old and new implementations for a subset of requests", before moving tables ([GitHub](https://github.blog/engineering/infrastructure/partitioning-githubs-relational-databases-scale/)).

Stripe's 2017 post is still the single best narrative of steps 1 to 7 for a payments company: "hundreds of millions" of Subscription objects moved out of an array on Customer records with no maintenance window, reads compared through Scientist with an alert on any mismatch, and switched only "After we verified that everything matched up" ([Stripe](https://stripe.com/blog/online-migrations)). It is also incomplete in ways the article should respect: it gives no durations, no mismatch counts, no ramp percentages, and does not say how the read switch was gated or how rollback worked after phase 3. Two rules emerge across the accounts. Reads are easy to gate and compare per request, writes are not: GitHub says "we only use Scientist on read operations" because a candidate that writes to the same database is "dangerous and incorrect" ([GitHub Scientist](https://github.blog/developer-skills/application-development/scientist/)), and Uber validated read endpoints by double execution but covered writes with tests and then moved write traffic by percentage ([Uber](https://www.uber.com/blog/schemaless-rewrite/)). And a flag that selects the authoritative store needs stronger consistency than an ordinary feature flag: Noah's boolean flags were evaluated inconsistently because of caching and deployment, so "different parts of the system occasionally had conflicting views of which ledger was active" ([Noah](https://noah.com/blog/zero-downtime-migration-of-noahs-internal-ledger)). Everyone else used a routing token (Stripe DocDB's "versioned gating"), a short write pause (GitHub, Shopify), or a scheduled window (Notion, LinkedIn).

GitLab's documentation is the most detailed public statement of the "schema works with version N and N-1" rule, and it shows the price. Dropping a column takes three releases (ignore it, drop it, remove the ignore rule) because Rails caches columns at boot and "dropping a column is a destructive operation that can't be rolled back easily"; renaming a table goes through a compatibility view; and under canary deploys "it is possible that the system runs in this state for a significant amount of time" ([GitLab](https://docs.gitlab.com/development/database/avoiding_downtime_in_migrations/), [GitLab rename tables](https://docs.gitlab.com/development/database/rename_database_tables/)). GitLab's procedures are driven by release order, not by a per-user flag. The vendor tool pgroll goes furthest toward literally "two versions of a column side by side": it keeps old and new physical columns in sync with triggers for the whole migration, so a client chooses a version with `search_path` ([pgroll](https://github.com/xataio/pgroll)). No independent production account of pgroll at scale was found, and version selection is per connection, which maps to "old app version versus new app version" rather than to a per-user flag.

The same choice exists for analytical tables in a lakehouse, where the table format rather than a migration tool decides what coexists. Delta Lake can add a column without rewriting data, and can rename, drop or widen a column through metadata, but all of these change the table's single current schema for every reader; v1 and v2 coexist only as an additive column beside the old one, as two views over one table, or as a separate `_v2` table built in parallel ([Delta docs](https://docs.delta.io/latest/delta-batch.html), [column mapping](https://docs.delta.io/latest/delta-column-mapping.html)). That ordering (additive column, then views, then a parallel table, with in-place rename or full schema overwrite as the "big bang" options) is the researchers' inference from the documentation. The in-place options carry costs the expand/contract steps avoid: column mapping is an irreversible protocol upgrade that older clients cannot read, and on Databricks "Updating a table schema terminates any streams reading from that table" ([Databricks](https://docs.databricks.com/aws/en/delta/update-schema)). Iceberg tracks columns by ID, so its schema changes are "independent and free of side-effects, without rewriting files" ([Iceberg](https://iceberg.apache.org/docs/latest/evolution/)), but that, too, changes one schema rather than keeping two.

## The ten-table chain is documented link by link, never whole

The second scenario is where the public record thins out. The researchers' honest summary is: each link of the chain is documented by its implementers; the whole chain, run as one progressive release, is not. Published end-to-end stories cluster at the two ends. At the source, companies forbid breaking change: LinkedIn's 2012 pipeline allowed only additive Avro changes ("new fields can be added, but must have a default value") with a failed compatibility check producing "a fatal error" ([LinkedIn 2012](http://sites.computer.org/debull/A12june/pipeline.pdf)), and Shopify says "Breaking schema changes are extremely disruptive for our downstream consumers, so we do our best as a company to avoid them whenever possible" ([Shopify](https://shopify.engineering/capturing-every-change-shopify-sharded-monolith)). At the model, companies shadow, canary and A/B test. The middle, the parallel intermediate tables, appears in first person only implicitly. The researchers' explanation, which is inference, is that large firms avoid the scenario by forbidding breaking source changes and by logging served features, so a "new schema" reaches a model as new columns in a log rather than as a second pipeline; the parallel-pipeline design is what a warehouse-centric team needs when neither holds, which describes many banks.

The design principle that makes steps 8 to 10 safe is stated directly by the feature platforms: the unit is "one model, one named feature set." Feast's 2026 design note uses the reader's scenario as its motivating case ("model A uses v1 features, model B uses v2 features") and rejects a shared table with a version column because "a model trained against v1 of a feature must retrieve v1 rows, not v2 rows that happen to occupy the same table" ([Feast](https://feast.dev/blog/feature-view-versioning)). A feature flag or experiment therefore selects a model, and the feature version follows from the model, never from the flag directly; Hopsworks puts it as "versioning the model alone is not enough" ([Hopsworks](https://docs.hopsworks.ai/latest/concepts/fs/feature_group/versioning/)). Databricks makes the same point by omission: its point-in-time lookups "are not related to Delta Lake time travel", and a logged model is bound to table and feature names with no table-version parameter documented, so the chain must keep v1 and v2 feature tables alive for the whole experiment and backfill v2's history before model B can train ([Databricks point-in-time](https://docs.databricks.com/aws/en/machine-learning/feature-store/time-series), [Databricks training](https://docs.databricks.com/aws/en/machine-learning/feature-store/train-models-with-feature-store)). Booking.com's design is the one to cite for a fair model comparison: the control group "invokes and uses the output from model 1, the current baseline, and also works as a safety net", and in both treatment arms "the outputs from both models are required", which removes latency as a confound and lets analysis focus on requests where the models disagree ([Booking](https://doi.org/10.1145/3292500.3330744)). Computing both models in both treatment arms doubles inference and feature-fetch cost there; that is the price of fairness.

How the publish step is done decides what the ten downstream tables see, and the tools differ in mechanism rather than in quality. Iceberg's WAP publish moves a snapshot pointer, so it costs almost nothing ([Iceberg](https://iceberg.apache.org/docs/latest/branching/)). On open-source Delta there is no native WAP; the documented route is a shallow clone, changes and checks on the clone, then a hand-written MERGE back into production ([Delta](https://docs.delta.io/latest/delta-utility.html)), and a lakeFS author who sells the alternative rates it "Fiddly, to say the least" ([lakeFS](https://lakefs.io/blog/how-to-implement-write-audit-publish/), vendor). That copy-style publish costs compute in proportion to the data changed, but it reaches downstream tables that read Delta's Change Data Feed as ordinary row changes, whereas swapping consumers onto a cloned table breaks them, because a clone starts its own history at version 0; one anonymous team on GitHub reported exactly that friction and called its replica-and-merge approach "not very efficient" ([discussion #4135](https://github.com/delta-io/delta/discussions/4135)). Both points are the researchers' inference from the documentation plus that one account. For atomicity across all ten tables, the Databricks route is to build the v2 tables in a separate schema, audit them, and rewrite the ten production tables inside one `BEGIN ATOMIC` block, with a `SIGNAL` statement to abort if a final check fails ([Databricks](https://docs.databricks.com/aws/en/transactions/)); consumers then see all ten change at one commit point, though rollback is still table by table because RESTORE cannot run inside a transaction. lakeFS gives real branch-and-merge across many Delta tables, but it works on path-based tables while Databricks transactions require catalog-managed tables, which the Delta protocol says cannot be accessed through the file system ([Delta protocol](https://github.com/delta-io/delta/blob/master/PROTOCOL.md)); the researchers infer that a team must choose one or the other for the same tables, though no source states the incompatibility.

An alternative to the backfilled v2 chain exists and is the one large firms often choose: log features at serving time and train on the logs. Google's Rules of ML recommends it (Rule #29) and reports that "YouTube home page switched to logging features at serving time with significant quality improvements" ([Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)); Uber Eats built a new training table from logged features beside the old ETL table. The cost is calendar time: Chronon's README warns "It might take a long to accumulate enough data to train the model" ([Chronon](https://raw.githubusercontent.com/airbnb/chronon/main/README.md)), and Netflix, which logs raw facts and regenerates features, says regeneration "takes hours compared to weeks taken by the feature logging" ([Netflix, mirror copy](https://noise.getoto.net/2022/04/26/evolution-of-ml-fact-store/)).

## Event streams change by new topic, second job and switched readers

Streams have the oldest written-down progressive procedure for data and the thinnest record of anyone following it with numbers. Two mechanisms do the work. A schema registry rejects any new event schema that breaks the configured compatibility rule, which is a machine-enforced version of "N and N-1 coexist". And a stream job is changed by running a second copy beside the first, not by editing it in place.

The compatibility mode fixes the order in which producers and consumers must upgrade. Confluent's documentation states it directly: under BACKWARD, "upgrade all consumers before you start producing new events"; under FORWARD, first upgrade all producers and make sure old-schema data is no longer available to consumers, then upgrade the consumers; under FULL, "you can upgrade the producers and consumers independently" ([Confluent](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html), vendor). BACKWARD is Confluent's default "so that you can rewind consumers to the beginning of the topic", but it is non-transitive: it checks a new version only against the one before it, so a chain of individually compatible changes can leave version X unreadable against X-2. The researchers infer that any consumer that replays from the start of a long-retention or compacted topic needs a transitive mode. Kafka Streams is the exception to "consumers first, then producers, and nothing else to worry about": because a Streams application also reads its own state and changelog topics, which still hold old-schema data, "The Kafka Streams apps must be upgraded first, then it's safe to upgrade the upstream producer" (same page). The format rules sit underneath. Protobuf's guide says "Field numbers should never be reused" and lists leaked personal data and data corruption as consequences ([protobuf.dev](https://protobuf.dev/programming-guides/proto3/)); in Avro, a rename is itself a two-step parallel change, "first update all readers of the data to use the new field name, while keeping the old name as an alias", then the writers ([Kleppmann 2012](https://martin.kleppmann.com/2012/12/05/schema-evolution-in-avro-protocol-buffers-thrift.html)). Default modes differ across Confluent, Pulsar, AWS Glue, Google Pub/Sub and Zalando's Nakadi; the appendix lists them.

A breaking change leaves the registry's world, and the public pattern is "forbid or fork". LinkedIn (2012) and Zalando forbid: Zalando requires full compatibility for anything the data lake ingests and says that under its compatible modes "MAJOR breaking changes are not allowed" ([Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/)). Yelp forks automatically, and its 2016 account is the clearest first-person description of versioned topics: "Only compatible schemas can use the same topic. When an incompatible schema is registered, the Schematizer creates a new topic in the same namespace and source", and consumers "have the flexibility to transition to the newer topics based on their own timeline" ([Yelp](https://engineeringblog.yelp.com/2016/08/more-than-just-a-schema-store.html)). Yelp also treats a primary-key change and the arrival of a personal-data field as breaking even when the format would allow them, because the key drives log compaction. Nakadi puts the major version in the event type name, so a breaking change is a new event type ([Nakadi](https://nakadi.io/manual.html)). Confluent's documentation is candid about the cost of the fork: moving consumers to a new topic is "complex because you must switch consumers from the old topic to the new topic without skipping data or processing it twice", and switching back needs the same offset correlation in reverse ([Confluent data contracts](https://docs.confluent.io/platform/current/schema-registry/fundamentals/data-contracts.html), vendor). Its alternative, "migration rules" that transform messages between major versions at read time inside one topic, is the one mechanism that resembles a flagged rollout of a breaking change, since each consumer opts into a major version by configuration; it is licensed, and no field report of it was found.

For the stream job itself, Jay Kreps's 2014 essay remains the canonical procedure: "start a second instance of your stream processing job that starts processing from the beginning of the retained data, but direct this output data to a new output table", then "When the second job has caught up, switch the application to read from the new table", then stop the old job and delete the old table ([Kreps 2014](https://www.oreilly.com/radar/questioning-the-lambda-architecture/)). Keeping both tables "allows you to revert back instantaneously to the old logic by just having a button that redirects the application to the old table", and for important cases "you can control the cut-over with an automatic A/B test or bandit algorithm". That last sentence is the only source in this research that proposes an A/B test between two data outputs, and it is a proposal, not a report. The limit is retention: "if you want to reprocess up to 30 days of data, set your retention in Kafka to 30 days." Uber could not meet it. It limits "Kafka retention to only a few days. Therefore, we're unable to adopt the Kappa architecture", and instead runs the same streaming code against archived Hive data ([Fu and Soman, SIGMOD 2021](https://arxiv.org/pdf/2104.00087)). Wise took the opposite route and keeps original event streams in compacted topics so new job versions can re-consume, for example, "one year's worth of data" ([Wise on Streaming Audio](https://developer.confluent.io/podcast/running-hundreds-of-stream-processing-applications-with-apache-kafka-at-wise)), though compaction keeps only the latest value per key, so this is not a full history (inference from Kafka's compaction definition).

Grab's May 2026 post is the only first-person account of an automated shadow stage for stream jobs. A new Flink version runs in a shadow namespace; its Kafka consumer group gets a `-shadow` suffix "to consume a full copy of the data stream without interfering with the Main application", its Debezium server-ID range shifts so it gets its own binlog stream, its Kafka output goes to a shadow cluster "with auto.create.topics.enable=true and 8h retention", and its S3 output to a bucket with "a 7-day retention lifecycle policy" ([Grab](https://engineering.grab.com/enchancing-flink-shadow-testing)). The shadow "runs for a configured period of 1 hour by default", and success is judged by job health; users can compare message rates between main and shadow sinks. The motivation was a production-only failure class (a new version unable to resume from the old version's checkpoint or savepoint), which previously surfaced only after a 10-minute automatic-rollback window and caused about that much downtime. The comparison is health and throughput, not output content: record-level diffing of two stream jobs' output is undocumented in every source the researchers could read.

State is what makes a stream job unlike a stateless service, and it is where the second-copy pattern becomes mandatory rather than optional. Flink supports state schema evolution "only for POJO and Avro types", and "Schema evolution of keys is not supported" ([Flink](https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/fault-tolerance/serialization/schema_evolution/)); changing the input or output type of a window, join or built-in aggregation "breaks application state consistency and prevents an upgrade", and Flink "cannot revert writes to external systems" ([Flink upgrading](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/upgrading/)). Spark Structured Streaming is stricter: "any changes (that is, additions, deletions, or schema modifications) to the stateful operations of a streaming query are not allowed between restarts" ([Spark](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html)). Kafka Streams' reset tool, the in-place route to reprocessing, requires every instance to stop, does not reset output topics, and warns "This tool makes irreversible changes to your application" ([Kafka](https://github.com/apache/kafka/blob/trunk/docs/streams/developer-guide/app-reset-tool.md)); adding an operator can rename internal state stores and changelogs so that "you can't do a rolling re-deployment" ([Kafka](https://github.com/apache/kafka/blob/trunk/docs/streams/developer-guide/dsl-topology-naming.md)). Wise's principal engineer said in 2021 that "in the Kafka Streams right now, there is no way to roll back your state in a consistent manner", so corrupted state means wiping it and replaying ([Wise](https://developer.confluent.io/podcast/running-hundreds-of-stream-processing-applications-with-apache-kafka-at-wise)). The researchers infer that a copy under a new application ID or consumer group is the non-disruptive alternative; the Kafka docs do not prescribe it.

Change data capture adds a coupling that the article's ten-table scenario should name. With CDC, the table schema is the event schema. Debezium's MySQL connector records every DDL statement so it can decode older log positions ([Debezium MySQL](https://debezium.io/documentation/reference/stable/connectors/mysql.html)), but its Postgres connector cannot see DDL at all: "Logical decoding does not support DDL changes" ([Debezium Postgres](https://debezium.io/documentation/reference/stable/connectors/postgresql.html)). Gunnar Morling, formerly Debezium's lead, names the risk ("Your table model becomes your API") and the remedy: an outbox table written in the same database transaction as the business change, whose contract can evolve separately, so that renaming a column in the event becomes "a conscious decision", or a stream job that republishes a contracted stream, including "creating multiple output versions for one input stream" ([Morling 2023](https://www.morling.dev/blog/change-data-capture-breaks-encapsulation-does-it-though)). Both cost something: every write path must emit the outbox row, with "a potential performance impact" at high volume. The researchers infer that without an outbox or contract layer, each step of an expand/contract column change upstream is visible to every stream consumer, and the registry's compatibility mode decides whether the final drop is accepted.

Rollback in streams undoes future writes, not history. Kafka's transactions give exactly-once only for "reading, processing and writing data on Kafka topics" ([Kafka design](https://github.com/apache/kafka/blob/trunk/docs/design/design.md)); a compacted topic keeps the latest value per key, so a bad value persists until overwritten. Monzo, which says "it's only a matter of time before a partition contains a poison pill", moves events that fail after a set number of attempts to a dead-letter topic per consumer group and replays them after the fix ([Monzo](https://monzo.com/blog/how-we-built-a-queue-on-top-of-kafka)). The researchers draw two inferences that no source states as an incident: rolling a producer back to the old schema is itself a new registry check that may fail under BACKWARD if the new version removed a field, and once consumers upgraded first under BACKWARD, rolling a consumer back after the producer has shipped is unsafe, so teams that want to roll back either side independently need FULL compatibility.

Streaming features for ML combine both problems. Chronon locks online feature groups and recommends a `_v2`, and says of online-offline consistency that "While 100% consistency is desirable, it is not always possible" ([Chronon](https://chronon.ai/test_deploy_serve/Online_Offline_Consistency.html)). That is the researchers' inference. Uber's 2020 Kappa+ post (tool-extracted) describes a backfill of about nine days of data, about 10 TB, taking on the order of a day ([Uber](https://www.uber.com/blog/kappa-architecture-data-stream-processing/)). Nubank's observation, from its own data platform, applies here too: "we rarely run into issues due to upstream data schema changes breaking analysis downstream"; the harder problem is "changes of 'data values' upstream", which it calls "still far from a solved problem" ([Nubank](https://building.nubank.com/microservices-at-nubank-an-overview/)).

Runtime costs are documented qualitatively. Notion's dark reads "increased API latency"; Uber's double execution doubled storage requests and had to be sampled; Uber Mezzanine used "a probabilistic approach to control the additional load" because the old database was already overloaded; and Stripe called converting every write path "arguably the most challenging part of the migration" across "thousands of lines of code across multiple services". Uber Eats' serve-time feature logging ran about 1.7 PB/day before compression (tool-extracted, [Uber](https://www.uber.com/blog/taming-ml-firehose/)). The CDC outbox costs a write on every write path and extra disk at high volume ([Morling](https://www.morling.dev/blog/change-data-capture-breaks-encapsulation-does-it-though)). A copy-style publish, which is what write-audit-publish becomes on open-source Delta, costs compute in proportion to the data changed, while a pointer-move publish costs almost nothing (researchers' inference from the Delta and Iceberg documentation).

In the analytical chain the dominant cost is not duplicate storage but backfill, because a v2 table or feature is useless until its history is recomputed, and for chained tables the recompute is sequential. Airbnb admitted that "backfills often could not catch up with user changes, especially when updates affect many datasets", so a fast-changing dataset "could end up in backfill mode forever"; its fix was a shared staging environment that backfills pending changes before they merge ([Airbnb](https://medium.com/airbnb-engineering/airbnb-metric-computation-with-minerva-part-2-9afe6695b486)). Netflix reports that late-data lookback windows cost "almost X times more" (X the window in days), and that rebuilding a 14-day-window pipeline incrementally used about 10% of the resources ([Netflix](https://netflixtechblog.com/incremental-processing-using-netflix-maestro-and-apache-iceberg-b8ba072ddeeb)). Tecton files in-place feature redefinition under cost: re-materialization "incurs cost and downtime" ([Tecton](https://docs.tecton.ai/docs/manage-costs/suppress-recreates)). DoorDash's embedding pipelines ran "about 10 to 12 hours every day", so one change took a day to propagate ([InfoQ](https://www.infoq.com/presentations/fabricator-ml)). dbt's own documentation names the trade-off between migrating consumers and "the cost (and clutter) of materializing multiple versions" and says sunsetting versions "requires real work, and likely significant coordination across teams" ([dbt](https://docs.getdbt.com/docs/mesh/govern/model-versions)). The originators of versioned signals priced it in 2015: "Versioning carries its own costs, however, such as potential staleness and the cost to maintain multiple versions of the same signal over time" ([Sculley et al.](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)). Old versions accumulate because removal is gated by model references and done by hand: Feast's design records "No mechanism to prune old versions" ([Feast ADR-0008](https://docs.feast.dev/project/adr/adr-0008-feature-view-versioning)), the data equivalent of the flag debt the essay already discusses. In streams the contract step is bounded by the slowest consumer plus topic retention, and a compacted or infinite-retention topic has no natural end (inference).

## Where it breaks: outages, drift, one-way switches and silent months

The operational-database failures come from the migration machinery itself. GitHub reported that trigger-based tools before gh-ost "would consistently cause MySQL outage" and that "the master is brought down by the load of the triggers" even while row copy was throttled ([GitHub](https://github.blog/news-insights/company-news/gh-ost-github-s-online-migration-tool-for-mysql/)). On 27 November 2021, the final rename step of a schema migration on a large table put a significant portion of GitHub's read replicas into a semaphore deadlock and crash recovery, and core services were unavailable for 2 hours 50 minutes; GitHub paused schema migrations afterward ([GitHub](https://github.blog/news-insights/company-news/github-availability-report-november-2021/)). GoCardless "took around 15 seconds of unexpected API downtime during a planned database migration" when a foreign-key lock queued behind a long-running read, though the same migration took a few hundred milliseconds against a backup ([GoCardless](https://gocardless.com/blog/zero-downtime-postgres-migrations-the-hard-parts/)). Shopify showed by experiment that an LHM migration can silently lose rows for one combination of NOT NULL, default, unique index and strict mode ([Shopify](https://shopify.engineering/add-not-null-colums-to-database)). Dual-written copies drift: Notion rejected application dual writes because "any issue with either write can quickly lead to inconsistencies between databases"; LinkedIn said "It is extremely hard to implement dual write with distributed transactions between two systems" and ran four separate verification loops; and Aircall (June 2026) found that a default reindex backfill "would have silently overwritten 13.5M newer documents with stale copies" of about 850 million while reporting zero failures, caught only by a pre-flight count check ([Aircall](https://aircall.io/en-gb/blog/tech-team-stories/elasticsearch-to-opensearch/)). Several switches were not online at all: Notion's five-minute window, LinkedIn's per-customer unavailability window on Sunday mornings, Figma's ten seconds of partial availability, Stripe DocDB's under-two-second rejection of requests. "Zero downtime" in these accounts usually means seconds of rejected or retried writes. And some migrations are one-way: LinkedIn's old and new Recruiter models were not one-to-one, so "it is not practical to go back and forth between the two systems."

The researchers distil four situations in which the operational pattern stops working or stops being cheap, an inference supported by these cases: the two models are not mutually convertible, so there is no rollback after the switch (LinkedIn); the old database is too loaded to bear triggers, backfill or comparison reads (Notion, Uber, GitHub before gh-ost); writes cannot be compared or replayed safely, so only reads get shadow-tested (GitHub, Uber); and the authoritative-store switch needs atomicity that ordinary flags do not give (Noah).

The analytical and ML failures are different in kind: the change is legal at its origin, passes type checks, and degrades rather than breaks the model, so a human notices weeks or months later. Uber's fares dataset lost a fare component because "an app experiment that started logging fares differently"; it was "detected after 45 days manually by one of the data scientists" and Uber estimates such incidents at millions of dollars; partial-data incidents took five times longer to detect than ETL or infrastructure failures ([Uber D3](https://www.uber.com/blog/d3-an-automated-system-to-detect-data-drifts/)). The upstream change there was itself a flagged experiment whose data side effect was not carried through the chain, which is directly relevant to the article. Google Play "once had a table that was stale for 6 months, and refreshing the table alone gave a boost of 2% in install rate" ([Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)). A Google video-recommendation migration silently dropped features because a backend stored them in a different format; with validation "The total time to diagnose and fix the problem was two days, whereas similar issues have taken months to resolve" ([Breck et al.](https://mlsys.org/Conferences/2019/doc/2019/167.pdf)). Google Research's data-cascades study found drift-type cascades taking "up to 2-3 years" to manifest ([Google Research](https://research.google/blog/data-cascades-in-machine-learning/)). Lyft reports that bad Hive data "caused tainted experimentation metrics, inaccurate machine learning features, and flawed executive dashboards" ([Lyft](https://eng.lyft.com/from-big-data-to-better-data-ensuring-data-quality-with-verity-a996b49343f6)). Structural gates do not catch these: dbt lists "Changing logic behind a metric", granularity and filters as changes that "might be breaking depending on your business logic", which its contracts cannot detect ([dbt](https://docs.getdbt.com/best-practices/how-we-mesh/mesh-6-coordinate-versions)), and LinkedIn's canonical example of a semantic change is a time field moving from seconds to milliseconds ([LinkedIn](https://engineering.linkedin.com/blog/2017/11/dali-views--functions-as-a-service-for-big-data)). Model-level canaries do not catch them either, because the model is not what changed. Sculley et al. located the cause in 2015: unstable data dependencies arise "when the engineering ownership of the input signal is separate from the engineering ownership of the model that consumes it", and even "'improvements' to input signals may have arbitrary detrimental effects" ([Sculley et al.](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)).

Lakehouse tables add failure modes that come from treating a table rollback as an undo. A Delta RESTORE is "considered a data-changing operation", so streaming readers treat the restored files "as newly added data" and process them again; it fails outright if cleanup has removed the target version's files ([Delta](https://docs.delta.io/latest/delta-utility.html)). Plain Delta streaming sources accept only appends: "Structured Streaming does not handle input that is not an append and throws an exception if any modifications occur on the table being used as a source", and the options are to restart from scratch, skip the changed commits (so "downstream does not see rows from those commits"), or accept duplicates ([Delta streaming](https://docs.delta.io/latest/delta-streaming.html)). An upstream v2 publish by overwrite therefore reaches downstream either as row changes each derived table must merge, or as a break that needs a restart or backfill (researchers' inference). In-place column renames and type widening upgrade the table protocol so older clients can no longer read it ([Delta column mapping](https://docs.delta.io/latest/delta-column-mapping.html), [type widening](https://docs.delta.io/latest/delta-type-widening.html)). How far back any rollback can go is set by retention defaults, which are short (see the appendix).

Streams fail at state and order. Grab's motivating failure was a new Flink version "unable to resume from a production checkpoint or savepoint taken by the previous version", which its old 10-minute rollback window turned into about ten minutes of downtime ([Grab](https://engineering.grab.com/enchancing-flink-shadow-testing)). Kafka Streams cannot roll state back consistently (Wise), and its reset is irreversible. Upgrading producers before a Kafka Streams consumer breaks it even under the registry's default mode (Confluent). Flink restores re-emit data, which is fine for idempotent key-value sinks "but problematic in case of appends to a durable log such as Kafka" ([Flink](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/upgrading/)). And a lagging Delta stream whose log has been cleaned up does not fail: "This can result in data being dropped" ([Delta streaming](https://docs.delta.io/latest/delta-streaming.html)).

Feature stores add their own limits. Chronon states that "While 100% consistency is desirable, it is not always possible" for streaming features. Tecton will not apply in place changes that "would invalidate the checkpoint" of a windowed stream aggregate. Embeddings must be fully recomputed and cannot mix versions (Hopsworks' own example of a breaking change). Several products lack multi-version serving altogether (appendix). Uber's 2021 feature-metadata incident (tool-extracted) took several hours to resolve, and rollbacks were prolonged because one change touched hundreds of feature groups ([Uber](https://www.uber.com/blog/palette-meta-store-journey/)).

The model end has statistical limits. Across "23 comparisons (46 models)" at Booking.com, offline gain correlated with business gain at Pearson -0.1 (90% CI -0.45 to 0.27), so "Offline model performance metrics are only a health check"; as models converge the "disagreement rate goes down", and power with it; review labels arrive "months later" ([Booking](https://doi.org/10.1145/3292500.3330744)). Adyen says "in mature product orgs, AB tests often come back flat or insignificant" ([Adyen](https://www.adyen.com/knowledge-hub/the-ai-behind-uplift)). Adoption is slow even at leaders: Uber reached shadow coverage of "over 75% of critical online use cases" only in 2025 (tool-extracted, [Uber](https://www.uber.com/blog/raising-the-bar-on-ml-model-deployment-safety/)). No first-party post-mortem of a staged model rollout going wrong was found.

## Percentage ramps and cheap undo do not survive the move to data

The progressive-delivery toolkit translates to data piece by piece, but two of its load-bearing properties do not. The table summarizes; everything in the right-hand column is supported by the sources above, and the framing is the researchers' synthesis.

| Code technique | Data equivalent | What carries over | What does not |
| --- | --- | --- | --- |
| Dark launch | Dual-write, shadow table, write-audit-publish, shadow stream job, model shadow | Run the new path on real inputs with no consumer seeing it | Writes cannot be run twice safely; only reads get per-request comparison; stream shadows are compared on health, not content (Grab) |
| Feature flag | Flag or routing token choosing which copy is read, which output table a reader uses, or which model serves | Instant switch of the read path (Figma: seconds; Kreps's "button") | A flag choosing the authoritative store needs atomic consistency (Noah); the flag does not remove the need for the expanded schema, backfill or replayed state |
| Percentage ramp | Percentage of reads, of dual-written objects, of customers, of model traffic | Works for operational reads and model traffic (Aircall, Figma, Stripe, Uber) | No percentage exposure for a derived table: 5% of rows on a new derivation is not a coherent table. Analytical ramps go by consumer or job batch (Meta, dbt, Minerva); stream ramps go by consumer, one switch at a correlated offset (Confluent) |
| Automated health gate | Contracts, registry compatibility checks, data tests, row-count and checksum diff, drift checks, model blessing | Pre-publish gate is the main safety mechanism | Structural checks miss semantic change; business-metric auto-rollback not documented |
| Rollback | Restore a table to an earlier snapshot or version, repoint readers to the old stream output, revert a model artifact | One table, one reader or one model reverts in seconds | Downstream tables, features and trained models already built stay wrong until recomputed; a Delta restore re-emits rows to streaming readers ([Delta](https://docs.delta.io/latest/delta-utility.html)); retention bounds how far back any restore or replay can go; a producer rollback does not remove events already written; Meta notes CDC carries bad landed data forward |
| A/B test | Experiment assigning models; Kreps's proposed A/B or bandit cut-over between stream outputs | Mature ML teams already select models through the general experimentation platform (Booking, LinkedIn, Adyen, Meta) | Not documented across two live data models; decisions already taken (blocked payments) cannot be undone |

The defensible statement for the article is that for data, rollback is per table and fast, undo of downstream effects is a backfill, and the main safety mechanism is therefore the pre-publish gate plus versioned coexistence, not post-release ramping. Write-audit-publish exists precisely to avoid "the loss of trust that can occur if processed data is made available and then retrospectively withdrawn or fixed" ([lakeFS](https://lakefs.io/blog/data-engineering-patterns-write-audit-publish/)). For model decisions in payments the irreversibility is sharper: Stripe says blocked payments "are blocked, and so we can't know what their outcomes would have been" ([Stripe](https://stripe.com/guides/primer-on-machine-learning-for-fraud-protection)), and Adyen that "once we apply a decision on a transaction (e.g. block it for fraud likelihood) we do not have access to the outcome if we wouldn't have acted on it" ([Adyen](https://www.adyen.com/knowledge-hub/the-ai-behind-uplift)). Reverting the model restores behavior; wrongly declined customers, approved fraud and a training set labeled only where the bad model let outcomes be seen all persist. None of these limits argues for a release train, which has the same irreversibility with larger exposure; they argue for longer shadow, randomized control or holdout slices, and explicit cost budgets for them. That is the researchers' inference, consistent with the essay's thesis.

## Owners, contracts and consumer reviewers decide who can change a shared table

The technical recipes assume someone knows who reads a table and someone has the authority to change it. The organizational record says that assumption usually fails until it is made mandatory, and that the people who fix it are named owners, written contracts, consumer reviewers and data-quality alerts routed to owners. It also contains a deliberate counter-example to continuous change.

The ML literature named the hazard before the data-contract movement did. Sculley et al. (2015) describe undeclared consumers "silently using the output of a given model as an input to another system", whose coupling "can radically increase the cost and difficulty of making any changes" and which are hard to detect without "access restrictions or strict service-level agreements (SLAs)" ([Sculley et al.](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)). Google's Rules of ML asks teams to "Give feature columns owners and documentation" (Rule #11) and to "Clean up features you are no longer using" (Rule #22) ([Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)). Sambasivan et al.'s CHI 2021 interview study of 53 practitioners in high-stakes domains gives the cultural reason the work goes undone: "92% experienced at least one cascade", and data work is "not easily 'tracked' or rewarded, as opposed to models" ([Sambasivan et al.](https://storage.googleapis.com/gweb-research2023-media/pubtools/5936.pdf)). The sample is health, conservation, lending and similar fields, not warehouse schema changes at tech firms.

Data contracts are the producer-side answer. Andrew Jones started them at GoCardless in 2021 as a reaction to CDC sources, where breaking changes were made without knowing downstream use ([Jones 2021](https://andrew-jones.com/blog/data-contracts/)). His first-person account, hosted on the observability vendor Monte Carlo's blog, describes a company-wide roadshow, contracts in Jsonnet that provision BigQuery and Pub/Sub resources automatically when merged, and a deliberately slow change path: the process for changing a contract "is intentionally heavy" ([Jones, Monte Carlo blog](https://www.montecarlodata.com/blog-data-contracts/)). Consumers and producers began "working together to set the data requirements – something that rarely happened before", and producers learned "which teams to coordinate with regarding which data assets". Adoption was fastest for new inter-service streams and "slower" for analytics consumers; the only outcome claimed is qualitative. The six-month adoption figure conflicts between sources: about 60% of asynchronous inter-service events in this account, about 50% in GoCardless's own "6 months on" post ([GoCardless](https://medium.com/gocardless-tech/data-contracts-at-gocardless-6-months-on-bbf24a37206e)). Chad Sanderson's 2022 advocacy, written while at Convoy, frames CDC as treating the production schema "as a non-consensual API" and has producers "own a single contract for each entity (CRUD) or semantic event", evolved backward-compatibly ([Sanderson](https://dataproducts.substack.com/p/the-rise-of-data-contracts)). Benn Stancil, co-founder of the analytics vendor Mode, rejects the negotiated form as "impractical to achieve, impossible to maintain" and argues it "replace[s] a brittle technical system with a negotiating table" ([Stancil](https://benn.substack.com/p/data-contracts)). PayPal's template became the Open Data Contract Standard under the Linux Foundation's Bitol project (v3.0.0 on 2024-10-21, v3.1.0 on 2025-12-08), whose team, roles and support-channel sections are where ownership and who-to-tell live ([ODCS](https://github.com/bitol-io/open-data-contract-standard), [changelog](https://bitol-io.github.io/open-data-contract-standard/latest/changelog/)). The standard applies a deprecation policy to itself, announcing that fields will be removed in v4.0.0.

The production accounts show what contracts change in practice. Adevinta Spain makes each contract an immutable file in GitHub: "For any change, including schema changes, whether minor or major, a new contract version should be created", with a validity end date once a higher version exists; automating pipeline creation from the contract cut its time to usable data from about 5 days to about 30 minutes ([Adevinta](https://adevinta.com/techblog/creating-source-aligned-data-products-in-adevinta-spain/)). Monzo, with "over 100 independent, empowered teams" contributing to "12,000+ dbt models", found that "A schema change here broke downstream models there"; "Rather than reverting to central ownership", it made selected models "interfaces", which a team "explicitly declares as a governed contract for cross-team consumption", and enforces "an explicit owner team" and freshness tests in CI on every pull request ([Monzo 2026](https://monzo.com/blog/a-meshy-approach-to-data)). Saxo Bank's Protobuf schemas carry field- and message-level deprecation markers so consumers get "insight into your future plans for breaking changes", and schemas "changed in small increments are quickly approved" ([Saxo, Confluent blog](https://www.confluent.io/blog/distributed-domain-driven-architecture-data-mesh-best-practices/), vendor-hosted). Virgin Media O2 keeps contracts as YAML in GitLab and generates data-quality scans from their SLOs ([Google Cloud blog](https://cloud.google.com/blog/products/data-analytics/vmo2-uses-data-contracts-to-build-scalable-ai-and-data-products/), vendor co-written). The researchers infer that contracts slow change at the boundary on purpose, and that the reconciliation with "ship small, often" is Monzo's: many cheap changes inside a team, a slow, versioned interface between teams.

Ownership is made mandatory in the same accounts. Zhamak Dehghani's data-mesh articles give the data product owner responsibility for "when to change, revise and retire data and schemas" ([Dehghani 2019](https://martinfowler.com/articles/data-monolith-to-mesh.html)), which is the closest analogue to the article's flag owner. Uber's 2021 programme made ownership mandatory where it could not be inferred, which by its account stopped new unowned data from appearing, tiered datasets by business impact, and made schema-change reviewers mandatory; for mobile analytics events, producers and consumers can add themselves as reviewers, a consumer-registration mechanism ([Uber](https://www.uber.com/blog/ubers-journey-toward-better-data-culture-from-first-principles/), tool-extracted). Nubank requires "the dataset owner" in structured metadata, requires integration tests to pass before a table is published or changed, reviews pull requests "within one day", and puts "model inputs" in a stricter class with different expectations about "who should validate the changes" ([Nubank](https://building.nubank.com/scaling-data-analytics-with-software-engineering-best-practices/)), the only first-person rule found that raises approval requirements because a model consumes a table. JPMorgan's mesh catalog lets data product owners "know where their data is being used" because access is granted through it ([JPMorgan, AWS blog](https://aws.amazon.com/blogs/big-data/how-jpmorgan-chase-built-a-data-mesh-architecture-to-drive-significant-value-to-enhance-their-enterprise-data-platform/), vendor co-written). None of these is full decentralization: each pairs owners with a central platform and central rules, and Monzo's 2021 response to "Shared ownership is not so shared anymore" was a small central team ([Monzo 2021](https://monzo.com/blog/2021/08/10/spinning-up-an-analytics-engineering-team)). Thoughtworks' 2026 review names the failure mode, an IT department that "re-badges its old teams as 'domains'" without business ownership ([Thoughtworks](https://www.thoughtworks.com/en-ca/insights/blog/data-strategy/the-state-of-data-mesh-in-2026-from-hype-to-hard-won-maturity)); it is a consultancy and Dehghani's former employer.

Consumer review and deprecation are documented as a sequence but not with numbers. LinkedIn's 2021 warehouse migration built lineage and usage pipelines, identified "datasets with no dependency and low usage" as deprecation candidates, "sent emails to dataset users about the upcoming deprecation", and locked, archived and deleted them "after a grace period" whose length is not given ([LinkedIn 2021](https://engineering.linkedin.com/blog/2021/evolving-linkedin-s-analytics-tech-stack)). Meta found hand-drawn data-flow diagrams "does not scale" and built lineage from static analysis and runtime instrumentation, though for privacy controls rather than schema changes ([Meta](https://engineering.fb.com/2025/01/22/security/how-meta-discovers-data-flows-via-lineage-at-scale/)). The researchers' reading is that consumer registration takes three forms: explicit opt-in as a reviewer (Uber), implicit through access grants (JPMorgan, Monzo interfaces), and inferred from lineage and query logs (LinkedIn, Meta). No source states a standard notice period or says who pays for running both versions.

LinkedIn's Super Tables are the deliberate counter-example the article should include. The 2022 post starts from the problem: "Changes to the datasets or their sources are usually made without consulting with or even notifying all downstream consumers, occasionally resulting in breaking changes being deployed." Its remedy for its most shared tables was "well-defined governance policies for change management and communication and committed change velocity (e.g., monthly deployment of changes)", with upstream producers and downstream consumers both on the governing body, a "99+%" availability target, a migration guide for the dozen tables and views each Super Table replaces, and a stated lesson that "it is imperative to provide awareness and support to the downstream users who need to perform the migrations" ([LinkedIn Super Tables](https://engineering.linkedin.com/blog/2022/super-tables--the-road-to-building-reliable-and-discoverable-dat)). That is a scheduled release cadence chosen on purpose for a heavily shared data product. The researchers' reading is that it does not contradict the essay's argument so much as locate its limit: where one table has many consumers who must each migrate, a predictable cadence is a service to them, and the cost of the train falls on the producer's speed rather than on consumer safety.

Data on-call exists mainly as alerts to owners and subscribers, rarely as paging. Uber reported tests on over 2,000 critical datasets catching about 90% of data-quality incidents, alerts routed to owners from metadata, and features to notify all downstream tables through lineage ([Uber](https://www.uber.com/blog/operational-excellence-data-quality/), tool-extracted, with no stated method for counting missed incidents). LinkedIn's Data Health Monitor watches "about 150k critical datasets" and sends email alerts to more than 2,000 consumer subscriptions within "roughly 30 minutes", and names "email alert fatigue" as the problem ([LinkedIn 2022](https://engineering.linkedin.com/blog/2022/towards-data-quality-management-at-linkedin)). incident.io's own data team runs a weekly "Data Responder" during working hours and routes failures with customer-facing impact to the product on-call engineers ([incident.io](https://incident.io/blog/how-our-data-team-handles-incidents), a vendor writing about itself). A practitioner on OpsGenie on-call lists the pain points: "lack of data lineage" and "Who owns the upstream source… Are they aware?" ([Sahlin](https://robertsahlin.substack.com/p/the-madness-of-data-incident-management)). Industry incident statistics, such as 67 incidents a month and four hours or more to detect for 68% of respondents, come from a survey commissioned by Monte Carlo, which sells monitoring ([Monte Carlo](https://www.montecarlodata.com/blog-data-quality-survey/)). No source measures fewer breaking-change incidents after contracts or ownership were introduced.

## Payments firms and banks supply fragments, not the chain

The financial-services record is the strongest at the operational end. Stripe's 2017 Subscriptions migration and its 2024 document-database platform (5 million queries per second, 2,000+ shards, 1.5 petabytes moved in 2023, a traffic switch that "takes less than two seconds", and replication kept bidirectional so that traffic can be reverted to the source) are first-party and read in full ([Stripe 2017](https://stripe.com/blog/online-migrations), [Stripe 2024](https://stripe.com/blog/how-stripes-document-databases-supported-99.999-uptime-with-zero-downtime-data-migrations)). Uber's payments ledger migration supplies the only quantitative argument about how long shadow confidence takes, and the warning that "live shadow validation can't give strong guarantees about our corpus of rarely-accessed historical data", which forced an offline comparison of 760 billion records in a single job ([Uber](https://www.uber.com/blog/migrating-from-dynamodb-to-ledgerstore/)); for a core-banking system with lower request rates, reaching the same confidence by shadowing takes longer, not shorter. Noah's QLDB-to-Aurora ledger move is the clearest small-company account of feature-flagged dual ledgers and their failure ([Noah](https://noah.com/blog/zero-downtime-migration-of-noahs-internal-ledger)). GoCardless supplies the lock-queue outage and the origin of data contracts. PayPal published its data-contract template without describing how consumers migrate between versions ([PayPal](https://github.com/paypal/data-contract-template)).

At the ML end, the banks and payments firms describe the stages without numbers. Monzo exports "a versioned snapshot" of each training dataset, uses "data validation queries implemented as ingestion preconditions", and says "we use shadow mode deployments extensively" ([Monzo](https://monzo.com/blog/2022/04/26/monzos-machine-learning-stack)); its former ML lead defines shadow as systems that "log data about all of their decisions, and then return a default value as if they were off", and names "low-volume/high-impact traffic (as is the case in fraud monitoring)" and regulatory guidance as reasons A/B testing may be impeded ([Lathia](https://nlathia.github.io/2020/07/Shadow-mode-deployments.html)). Nubank runs fraud models in shadow, where the model "processes real data but doesn't affect customer-facing decisions", against a 700ms PIX latency budget ([Nubank](https://building.nu.com/practices-to-scale-machine-learning-operations/)), and advises "Deploy the model in shadow mode as early as possible" ([Nubank](https://building.nu.com/de-risking-real-time-ml-projects-addressing-common-failure-modes/)). Adyen's lifecycle is ghost, challenger, principal, retired; its control group keeps a "market baseline" (blocking known-stolen cards and similar) so uplift is "lower, but more honest", and it reports off-policy estimates with "+80%" correlation to actual A/B tests, saving about 20 weeks a year of flat tests ([Adyen](https://www.adyen.com/knowledge-hub/the-ai-behind-uplift)). Stripe's Shepherd feature platform built monitoring on Chronon's online-offline consistency for a SEPA fraud model with "over 200 features" that "blocks tens of millions of dollars of additional fraud a year" ([Stripe](https://stripe.com/blog/shepherd-how-stripe-adapted-chronon-to-scale-ml-feature-development)), but neither Shepherd nor the Radar architecture post mentions shadowing, backfilling or ramping a new feature. The one regulated credit-data failure with primary documentation is Equifax's 2022 "coding issue within a legacy, on-premise server environment", which ran "between March 17 and April 6" and shifted scores by 25 points or more for "less than 300,000 consumers" ([Equifax](https://www.equifax.com/newsroom/all-news/-/story/equifax-statement-on-recent-coding-issue/)); the statement does not say whether it was an input or schema change. No bank or payments firm has published the complete chain, and no regulator enforcement action citing an ML input or schema change was found.

In streams, the event-driven banks describe scale, dead-lettering and replay rather than schema rules. Monzo dead-letters poison messages per consumer group; Wise holds about 50 TB of Kafka Streams state and keeps "pretty much the whole history of Wise of all the core domains" in compacted topics for replay ([Wise](https://developer.confluent.io/podcast/running-hundreds-of-stream-processing-applications-with-apache-kafka-at-wise)); Clear Street, a brokerage, moved from Avro to Protobuf after "problems with schema migrations using Avro that could potentially lead to massive rollbacks", without describing how the formats coexisted ([Clear Street](https://clearstreet.io/news/blog/switching-to-protobuf-from-avro-on-kafka)). The best-known "two versions side by side" in payments is industry-wide. According to search-result text of Swift pages, which refused automated access, Swift ran MT and ISO 20022 in parallel for cross-border payments from 20 March 2023 to 22 November 2025 ([Swift](https://www.swift.com/news-events/news/iso-20022-coexistence-begins-opening-new-possibilities-cross-border-payments)); according to search-result text of Federal Reserve pages, the Fedwire Funds Service moved in a single day on 14 July 2025, after postponing from 10 March 2025 on grounds of industry requests and customer readiness ([Federal Reserve Financial Services](https://frbservices.org/news/communications/061825-fedwire-iso-go)). The researchers read the contrast as the same choice the article describes, consumer-paced coexistence against a single cut-over, but every date here must be re-checked in a browser before printing.

## Regulators require validation before live use and accept parallel comparison, but none defines a traffic split

The question for each regulator is what it requires before a changed data pipeline or model affects decisions, whether it says anything about running two versions in parallel, and what it says about experiments on customers. The binding status differs and matters: EU regulations and Commission delegated regulations bind directly; EBA guidelines are comply-or-explain; EBA reports, ECB guides and most national principles papers are not binding law, though ECB guides state how the ECB applies the law to the banks it supervises.

### United States and United Kingdom

SR 26-2 (17 April 2026, Federal Reserve with OCC and FDIC) "supersedes and replaces SR letter 11-7" and is "expected to be most relevant to banking organizations with over $30 billion in total assets" ([SR 26-2](https://www.federalreserve.gov/supervisionreg/srletters/SR2602.htm)). Its attachment says "Validation generally occurs prior to a model's first use", allows earlier use for urgent need with "placing limits on model use or more closely monitoring its performance", requires outcomes analysis that "compares model outputs to corresponding real-world outcomes", and takes generative and agentic AI out of scope; a search of the text found no occurrence of "parallel", "champion" or "challenger" ([SR 26-2 attachment](https://www.federalreserve.gov/supervisionreg/srletters/SR2602a1.pdf)). PRA SS1/23 (in force 17 May 2024) is more specific: development testing should compare output "with the output of available challenger models" where practicable; material changes, including changes over time in dynamic models, require before-and-after comparison against outcomes, which the PRA calls "parallel outcomes analysis"; monitoring includes benchmarking, sensitivity testing and analysis of overrides; and a decommissioned model "may be used as a challenger model itself" ([PRA SS1/23](https://www.bankofengland.co.uk/-/media/boe/files/prudential-regulation/supervisory-statement/2023/ss123.pdf)). Neither text prescribes production A/B tests or traffic splitting. SR 11-7's own wording could not be retrieved, so the article should not characterize what it said about parallel runs.

### Continental Europe: lineage, reconciliation and data change

BCBS 239 (January 2013, mandatory for global systemically important banks from 2016) requires risk data aggregation to be "Considered as part of any new initiatives", including "broader process and IT change initiatives", and says banks need not have one data model; "rather, there should be robust automated reconciliation procedures where multiple models are in use" ([BCBS 239](https://www.bis.org/publications/201301-guidelines-principles-effective-risk-data-aggregation-and-risk-reporting.pdf)). That footnote is the closest any banking standard comes to accepting two schemas side by side. The ECB's May 2024 guide on risk data aggregation and reporting, which applies these principles to the banks the ECB supervises directly, expects a central data governance function to take part in "change management processes with a material impact on RDARR", "complete and up-to-date data lineages on data attribute level (starting from data capture and including extraction, transformation and loading)", automated data-quality controls with tolerance levels from source systems to reports, and "periodical reconciliation" with sources and "related model development data" ([ECB RDARR guide](https://www.bankingsupervision.europa.eu/ecb/pub/pdf/ssm.supervisory_guides240503_riskreporting.en.pdf)). Its scope explicitly includes input data for IRB, Pillar 2, IFRS 9 and VaR model development. It also expects "Data owners responsible for key risk indicators and critical data elements" who define quality controls "in alignment with data users (or consumers)", which is close to the contract practice above. The guide names no deployment method: a search found nothing on parallel runs, dual tables or rollback. The ECB says this is still the weak point: RDARR was "the worst-rated sub-category of internal governance in the 2023 SREP cycle", and the 2025 results showed "no improvement in the relevant average sub-score" ([ECB priorities 2026-2028](https://www.bankingsupervision.europa.eu/framework/priorities/html/ssm.supervisory_priorities202511.en.html)). In Germany, MaRisk AT 4.3.4 requires risk data to be reconciled and plausibility-checked against other information in the bank, and AT 7.2 requires IT systems to be tested before first use and after material changes, with production and test environments "grundsätzlich" (in principle) separate ([MaRisk, Circular 06/2024](https://bundesbank.de/resource/blob/932738/fa6ddd3636c40c9f9d5cb4fad4f07121/mL/2024-05-29-rundschreiben-data.pdf)). The researchers infer that dual-running v1 and v2 tables and reconciling them before cut-over produces exactly the evidence these texts ask for (current column-level lineage, reconciliation, tolerances, governance involvement), and that an engineering team can present contracts, CI owner checks and lineage as RDARR evidence. No supervisor says either.

### Internal models: a regulatory clock that flags cannot shorten

For banks using internal ratings-based (IRB) models for capital, CRR Article 143 requires prior permission for material changes to a rating system and notification of "all changes to rating systems" ([CRR](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:02013R0575-20250629)). Delegated Regulation 529/2014 sorts changes into three classes: material (permission), ex ante notification "at least two months before their implementation", and ex post notification "at least on an annual basis"; a change may not be split to lower its class, and in doubt the higher class applies ([529/2014](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32014R0529)). Two of its ex ante items bear directly on the ten-table scenario: "change of the data sources used in the process of allocating exposures to grades or pools or for parameter estimation", and "inclusion of new or additional information in a model for parameter estimation". Swapping the upstream table under an IRB model is therefore a notifiable change in its own right, even if the numbers do not move. The researchers infer that a data team that does this without telling model risk management may cause a notification breach. The 2014 text was amended in 2015, and the EBA submitted a revised draft in March 2026 that would classify fewer changes as material and rely more on quantitative thresholds; the Commission's adoption of that draft was not verified ([EBA/RTS/2026/05](https://www.eba.europa.eu/sites/default/files/2026-03/7bbbbcd4-caa4-489d-b2b4-a837d04e709e/Final%20report%20RTS%20on%20material%20model%20changes.pdf)).

The ECB guide to internal models (v4.1, June 2026) adds the parallel run. A bank applying for a material change should be able to "fully replicate the execution of the model and the calculation of own funds requirements according to the model change in a non-live production environment", which the guide defines as "a parallel version of a live production environment that is already in place"; approved changes should go live within about three months of the decision ([ECB guide to internal models](https://www.bankingsupervision.europa.eu/ecb/pub/pdf/ssm.supervisory_guide_egim_202606.en.pdf)). For a change to the definition of default it allows "a parallel run (i.e. the implementation of the new definition of default in a parallel environment to the productive systems)", the nearest supervisory analogue to a schema change run in parallel. One terminology trap: the guide's "shadow rating models" are internal models that replicate external ratings, not shadow deployments. The guide's machine-learning section expects the first switch to a mostly ML-based model to be classed as material, and expects monitoring that can "prevent the automatic implementation of material changes". The EBA's 2023 follow-up report draws the line that matters for challengers: "as long as the rating system used to calculate own fund requirements is not updated, the model change framework does not constrain the use of self-training and self-development model challengers" ([EBA 2023](https://www.eba.europa.eu/sites/default/files/document_library/Publications/Reports/2023/1061483/Follow-up%20report%20on%20machine%20learning%20for%20IRB%20models.pdf)). The CRR also requires each in-scope exposure to be rated by "that rating system" (Article 144(1)(h)), so the researchers infer that a staged rollout of a changed IRB model across part of the portfolio does not fit the framework, while a shadow run on all exposures that is not used for capital does.

### Machine learning outside the capital calculation

The EBA's 2020 big data report, which is not binding, is the only EU-level text found that describes a production parallel run in deployment terms: "Optionally, the model may be deployed in production only after a parallel testing period during which the new candidate model (also called the 'challenger model') runs in parallel with the old system to enable a comparison of the results" ([EBA 2020](https://www.eba.europa.eu/sites/default/documents/files/document_library/Final%20Report%20on%20Big%20Data%20and%20Advanced%20Analytics.pdf)). It says deployment "should be integrated into the standard change management process", describes monitoring by comparing the ML model's outcomes "with those of the previous system running in parallel", and recommends registering all model versions so a bank can "compare different models or perform a roll-back if necessary". The EBA's loan-origination guidelines (comply-or-explain, from 30 June 2021) require automated credit models to have controls on input data quality and bias, traceability of inputs and outputs, back-testing, overrides and continuous monitoring, but say nothing about introducing a new model version ([EBA/GL/2020/06](https://www.eba.europa.eu/sites/default/documents/files/document_library/Publications/Guidelines/2020/Guidelines%20on%20loan%20origination%20and%20monitoring/884283/EBA%20GL%202020%2006%20Final%20Report%20on%20GL%20on%20loan%20origination%20and%20monitoring.pdf)). An ECB newsletter on workshops with 13 banks reports that "none of the banks in the sample permits self-learning after deployment", with the caveat that the sample is small ([ECB newsletter](https://www.bankingsupervision.europa.eu/press/supervisory-newsletters/newsletter/2025/html/ssm.nl251120_1.en.html)). The researchers infer that each retrain is a release that passes through change classification rather than an in-place update of the serving model.

### The AI Act after the 2026 omnibus

AI systems used "to evaluate the creditworthiness of natural persons or establish their credit score" are high-risk under Annex III point 5(b), "with the exception of AI systems used for the purpose of detecting financial fraud" ([AI Act](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32024R1689)). Regulation (EU) 2026/1744, the Digital Omnibus on AI, adopted on 8 July 2026 and in force since 27 July 2026, moved the high-risk obligations for Annex III systems to "2 December 2027" ([2026/1744](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32026R1744)). A change "not foreseen or planned in the initial conformity assessment" that affects compliance is a "substantial modification" (Article 3(23)) and requires a new conformity assessment (Article 43(4)); changes from continued learning that were "pre-determined by the provider" and documented are not. Credit-scoring systems already in use before the application date stay outside the Act until they undergo "significant changes in their designs" (Article 111(2) as amended), which recital 177 equates with substantial modification. Article 10(2) requires governance of training data covering its origin and "data-preparation processing operations, such as annotation, labelling, cleaning, updating, enrichment and aggregation"; Article 12 requires automatic logging over the system's lifetime. Testing a high-risk system on real people before it is placed on the market is allowed under Article 60, but only with an approved plan (tacit approval after 30 days), registration, a six-month limit extendable by six, informed consent, and decisions that "can be effectively reversed and disregarded". For banks, most of this folds into existing governance: the quality-management and monitoring obligations are deemed met by complying with financial-services governance rules, and the market surveillance authority is the financial supervisor.

The researchers draw four inferences, none stated in guidance. A model retrained on a new upstream schema, with redefined features or changed data preparation, is outside a typical pre-determined change plan and is likely a substantial modification unless the plan foresaw it. A schema-driven redesign of a legacy scorecard after 2 December 2027 may pull that system into full scope, which gives banks a reason either to land planned redesigns earlier or to document them as foreseen. Once a compliant system is in service the Act has no rule about routing customers between two versions, but each version must itself be compliant. And silent A/B testing of an unassessed credit model on applicants would not fit Article 60's consent condition.

### Customers' rights apply to every arm of an experiment

No EU text forbids serving two credit models to different applicants; every applicant keeps the same rights whichever model scored them. Under GDPR Article 22, a decision "based solely on automated processing" with legal or similarly significant effects is lawful only if necessary for a contract, authorised by law or based on explicit consent, and the person keeps "at least the right to obtain human intervention", to express a view and to contest the decision; Articles 13 to 15 require "meaningful information about the logic involved" ([GDPR](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32016R0679)). The CJEU's SCHUFA judgment (C-634/21, December 2023) held that a credit bureau's score is itself automated decision-making where a lender "draws strongly on that probability value" ([SCHUFA](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:62021CJ0634)). The Consumer Credit Directive (EU) 2023/2225, applicable from 20 November 2026, gives consumers whose creditworthiness assessment involves automated processing the right "to request and obtain from the creditor human intervention", including "a clear and comprehensible explanation of the assessment of creditworthiness, including on the logic and risks involved" and a review of the decision (Article 18(8)) ([CCD](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32023L2225)). The Article 29 Working Party's guidelines, endorsed by the EDPB, expect "frequent assessments" for bias and regular testing of credit-scoring methods, and say nothing about experiments ([WP251rev.01](https://ec.europa.eu/newsroom/article29/document.cfm?action=display&doc_id=49826)). The researchers infer the consequences for an experiment: the explanation must describe the model that actually scored each applicant, human review must be able to reproduce either arm's decision (so the model version must be logged per decision), and a shadow model that scores but does not decide produces no Article 22 "decision" at all.

### Payment fraud models: a fraud-rate limit makes a bad challenger a regulatory event

The PSD2 technical standards let a payment service provider skip strong customer authentication for low-risk remote transactions only while its overall fraud rate, calculated "on a rolling quarterly basis (90 days)", stays at or below reference rates (for remote card payments, 0.13% up to EUR 100, 0.06% up to EUR 250, 0.01% up to EUR 500); it must "immediately report" a breach and "immediately cease to make use of the exemption" after two consecutive quarters above the rate; and "the methodology, the model and the reported fraud rates" must be audited yearly, by an external auditor in the first year and at least every three years ([Delegated Regulation 2018/389](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32018R0389)). The standards say nothing about changing or testing the fraud model. The researchers infer that a challenger's fraud lands in the same provider-wide rate, so a worse challenger on a share of traffic risks the exemption for all customers in that band; exposure should be capped so that even a worst-case challenger cannot push the blended rate over the limit, the blended rate monitored continuously, and a flag kept to route all traffic back to the champion. Fraud models are excluded from the AI Act's credit-scoring category, so this, not the AI Act, is their binding constraint. The PSD3 and Payment Services Regulation negotiations were not checked.

### DORA: testing in production is an approved exception, and every change needs a way back

The DORA technical standard on ICT risk management, Delegated Regulation 2024/1774, binds banks, payment and e-money institutions and other financial entities and covers "all changes to software, hardware, firmware components, systems, or security parameters" ([RTS 2024/1774](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32024R1774)). Article 17(1) requires independence between "the functions that approve changes and the functions responsible for requesting and implementing those changes", changes "tested and finalised in a controlled manner", and "fall-back procedures and responsibilities, including procedures and responsibilities for aborting changes or recovering from changes not successfully implemented". Article 8(2) allows testing in a production environment only where instances "are clearly identified, reasoned, are for limited periods of time, and are approved by the relevant function", and requires the firm to protect production data during it. Article 16(5)(a) says "non-production environments only store anonymised, pseudonymised, or randomised production data", with a derogation for specific, time-limited, approved occasions reported to the ICT risk function. None of the DORA texts mentions canaries, flags, staged rollout or parallel runs. The incident classification standard, Delegated Regulation 2024/1772, makes an incident major when it affects critical services and meets two or more thresholds, which include more than 10% of clients or more than 100,000 clients affected, more than 10% of daily transactions, downtime over 2 hours for critical services, and any impact on the "availability, authenticity, integrity or confidentiality of data" that harms business objectives or compliance; non-major incidents that recur twice in six months with the same apparent root cause count together ([RTS 2024/1772](https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=CELEX:32024R1772)). Major incidents must be notified within four hours of classification ([RTS 2025/301](https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=CELEX:32025R0301)), and the final-report template has "change management" as a named root cause ([ITS 2025/302](https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=CELEX:32025R0302)).

The researchers draw these inferences for data work; no supervisor has stated them. A shadow run or dual-write that touches production may count as testing in production and so needs to be identified, reasoned, time-limited and approved, unless the firm frames it as a planned transition step within an already tested change. A clone or branch of a production table used for validation outside production is production data in a non-production environment unless it is anonymised or covered by an approved derogation, which pushes realistic validation toward controlled runs inside production. Rollback and abort procedures for pipelines, tables and models are required, not optional. Because data-integrity impact is itself a materiality threshold, a bad pipeline change can become a major incident without any downtime, while a defect caught at a small model ramp and reverted in minutes may stay below two thresholds; repeated small incidents with one cause can still aggregate into a major one.

### National supervisors

National texts are principles, not procedures, and none mentions randomized customer experiments. BaFin's 2021 principles paper (non-binding) says every algorithm "sollte vor Übernahme in den operativen Betrieb einen angemessenen Validierungsprozess durchlaufen" (should go through an appropriate validation process before going live), names "eine systematische Veränderung der Inputdaten" (a systematic change in input data) as a trigger for ad hoc revalidation, and proposes a tiered release process whose last stage is a "Stopping-Rule" that interrupts the process for review ([BaFin](https://www.bafin.de/SharedDocs/Downloads/DE/Aufsichtsrecht/dl_Prinzipienpapier_BDAI.pdf?__blob=publicationFile&v=1)), which the researchers read as a supervisor-proposed automated kill switch. MaRisk AT 4.3.5, binding administrative practice in Germany, requires suitability to be assessed "vor dem Einsatz eines Modells" (before a model is used) and applies explicitly to automated models and AI ([MaRisk](https://bundesbank.de/resource/blob/932738/fa6ddd3636c40c9f9d5cb4fad4f07121/mL/2024-05-29-rundschreiben-data.pdf)); a 2026 consultation may renumber it. DNB's 2019 discussion paper says material AI should be "regularly assessed by evaluating model outcomes against conventional (non-AI enabled) models", that models should be retrained and reassessed "especially in the event of significant changes in the input data", and that training data should be "systematically archived" ([DNB](https://www.dnb.nl/media/jkbip2jc/general-principles-for-the-use-of-artificial-intelligence-in-the-financial-sector.pdf)). The ACPR's 2020 discussion document lists challenger models as an audit technique, recommends archiving every production model version because retraining yields "non-reproducible decisions on a given input between subsequent versions", and concludes that ML internal models "become invalid following a major change in their input data" ([ACPR](https://acpr.banque-france.fr/sites/default/files/medias/documents/20200612_ai_governance_finance.pdf)). FINMA (Switzerland, not EU) assessed whether institutions test that an application works "before productive use, in the event of changes" and on an ongoing basis, monitor data drift, and have "fallback mechanisms" ([FINMA 08/2024](https://www.finma.ch/en/~/media/finma/dokumente/dokumentencenter/myfinma/4dokumentation/finma-aufsichtsmitteilungen/20241218-finma-aufsichtsmitteilung-08-2024.pdf)). No Banca d'Italia supervisory text on model change or AI testing was found.

### The common thread

| Text | Binding? | What it requires for a data or model change | What it says about parallel runs or experiments |
| --- | --- | --- | --- |
| SR 26-2 (US) | Supervisory guidance | Validation before first use; outcomes analysis | No mention of parallel, champion or challenger |
| PRA SS1/23 (UK) | Supervisory statement | Challenger comparison in development; before/after comparison for material changes | "parallel outcomes analysis"; no traffic split |
| BCBS 239 and ECB RDARR guide | Standard; ECB guide | Governance in data change, attribute-level lineage, automated controls with tolerances, reconciliation | Multiple data models acceptable with "robust automated reconciliation"; no deployment method |
| CRR Art 143, Reg 529/2014 | Binding | Permission or notification for IRB changes; changing data sources is ex ante, two months | No staged rollout across exposures (inference) |
| ECB guide to internal models | ECB guide | Full replication in a parallel non-live production environment before approval | Parallel run expected for material changes; definition-of-default parallel run allowed |
| EBA 2023 ML report | Non-binding | Retraining of the capital model goes through change classification | Challengers not constrained while the capital model is unchanged |
| EBA 2020 big data report | Non-binding | Deployment through change management; model version register for rollback | Optional parallel challenger period in production |
| AI Act as amended by 2026/1744 | Binding | High-risk credit scoring from 2 December 2027; substantial modification needs a new assessment | Real-world testing before market only with approval and consent; nothing on A/B between compliant versions |
| GDPR Art 22, SCHUFA, CCD Art 18(8) | Binding | Human intervention, explanation and review for automated credit decisions | Nothing forbids two models; rights apply to both arms |
| PSD2 RTS 2018/389 | Binding | Fraud rate under reference rates; audit of the model | Nothing on challengers; their fraud counts in the same rate |
| DORA RTS 2024/1774 and 2024/1772 | Binding | Independent approval, controlled testing, fall-back and abort; incident thresholds include data integrity | Testing in production only as an approved, time-limited exception |
| BaFin, MaRisk, DNB, ACPR, FINMA | Mixed | Validation before use; revalidation on input-data change; fallback | Comparison with conventional or challenger models; nothing on customer experiments |

Read together, the texts converge on three points. Validation comes before live use, everywhere. A parallel run that takes no decisions is either expected (ECB for IRB changes), described as good practice (EBA 2020, PRA, DNB), or explicitly unconstrained (EBA 2023), which makes a shadow run the stage that fits before sign-off. And no regulator defines or forbids a traffic-split experiment; a live challenger arm makes decisions, so it counts as use and needs prior validation, and in Europe it carries every customer right, the PSD2 fraud-rate limit, the IRB change clock and DORA's change controls with it. That synthesis is the researchers' inference; no regulator states it.

## Conclusion

The reader's objection is half right. Data changes can be shipped with dark launches, flags, comparison and staged switches, and the companies that publish about it (several of them in payments) have done so for a decade; but what gets staged is a parallel copy, a second stream job or a parallel model, and the expensive parts (expanded schema, backfill, replayed state, reconciliation, reverse sync) do not shrink because a flag sits in front of them. The useful reframing for the article is that a release train and a data migration share a property code rollouts lack: effects that leave the system cannot be recalled. Progressive delivery's answer for data is therefore "keep both versions alive, prove equivalence or improvement before consumers depend on the new one, and switch with a reverse path in hand". Kreps wrote that answer down for streams in 2014, with a button to repoint readers and an A/B test to choose between outputs, and twelve years later no one has published doing the A/B part. It is still an argument against the train, because the train ships the same irreversible change to everyone at once with less evidence.

Two findings should change how the article frames its recommendations. First, the boundary between teams is where data change is deliberately slowed: contracts are "intentionally heavy" to change, Adevinta makes every change a new version, and LinkedIn put its most shared tables on a monthly cadence. The defensible position is not that all data change should be continuous but that change inside a team can be small and frequent while the shared interface is versioned and paced for its consumers, with the producer paying for coexistence. Second, in European banking the data team cannot treat an upstream table swap as an internal matter: if the table feeds an IRB model it starts a two-month notification clock, if it feeds a credit model after December 2027 it may decide whether a new AI Act conformity assessment is needed, and if it feeds a fraud model under the PSD2 exemption a bad challenger can cost the exemption for every customer. Flags and shadow runs cannot shorten those clocks, but they produce the parallel-run and reconciliation evidence every one of these regimes asks for. That makes lineage from source table to regulated model the precondition for progressive delivery of data at a bank, not an optional extra.
