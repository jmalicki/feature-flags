# Chapter 2: Data and models

*Part of [Moving off the release train](README.md). How separating deployment from release applies to changes in tables, event streams, feature stores and machine-learning models.*

Many software changes are changes to data: a column split in an operational database, a new derivation in a reporting table, a feature recomputed for a model, or a model retrained on a different schema. These changes can also be released progressively, although the mechanics differ from those for code at almost every step, because rolling back the code that wrote a new version of a dataset does not bring the old version back. The release of a data change therefore keeps the new version beside the old one. A table is published only after checks on it pass, every changed feature gets a new version, each model is bound to the data versions it was trained on, and a model runs in shadow before it makes decisions.

This chapter uses the terms of [the first chapter](essay.md): to **deploy** is to put code into production and to **release** is to expose its behavior, a ramp widens exposure in stages, and a shadow run passes real input through new code and discards the result.

## Differences between data and code changes

A code change can be ramped because each request is handled on its own and the previous build still exists. A data change alters stored state that outlives the process that wrote it, and that state is read by jobs, tables, dashboards and models, many of which belong to other teams, so the effect of a bad change can go unnoticed for weeks. At Uber, an app experiment changed how fares were logged, and a fare component went missing from a critical fares dataset for a share of sessions in key US cities until a data scientist [found the gap by hand 45 days later](https://www.uber.com/blog/d3-an-automated-system-to-detect-data-drifts/). Sculley and colleagues at Google traced this class of fault to the situation that arises ["when the engineering ownership of the input signal is separate from the engineering ownership of the model that consumes it"](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf).

A percentage ramp still works for reads from an operational store and for traffic to a model, and Aircall [moved reads to a new search cluster at 5%, 25%, 50% and 100%](https://aircall.io/en-gb/blog/tech-team-stories/elasticsearch-to-opensearch/). A derived table cannot be ramped that way, because a table whose rows are 5% computed under a new derivation and 95% under the old one gives no reader a coherent answer. What is ramped instead is a parallel copy of the data, a second stream job or a model, and exposure grows by consumer or by batch of jobs. Meta, for example, [moved tens of thousands of ingestion jobs to a new system in batches](https://engineering.fb.com/2026/05/12/data-infrastructure/migrating-data-ingestion-systems-at-meta-scale/).

The main control for data is therefore a check before anything is published, together with a period in which the old and new versions are both available, because rollback reaches only one table at a time. [Iceberg](https://iceberg.apache.org/docs/latest/spark-procedures/) rolls a table back by moving its snapshot pointer, and Delta Lake writes the earlier version as a new commit, so [streaming readers process the restored files again as if they were new data](https://docs.delta.io/latest/delta-utility.html). Either way, an earlier version can be restored only until table cleanup has removed its files, and every derived table, feature and trained model built from the bad version keeps its contents until each is recomputed. Retention set long enough for rollback also keeps personal data that users have asked to have erased. The [GDPR](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32016R0679) requires erasure without undue delay, so an erasure has to reach every snapshot, branch and version of a table that can still be read.

Rolling back the source table, by moving an Iceberg snapshot pointer back or by a Delta Lake restore, returns only that table to its earlier version; the ten derived tables, the feature and the two models still hold data built from the bad version until each is recomputed.](figures/21-data-rollback.svg)

## Versions as the unit of release

If both versions are to be available at once, each needs its own name. LinkedIn's Dali system exposes shared datasets as more than 300 versioned views, and its engineers wrote that ["multiple versions of the same View can happily coexist"](https://engineering.linkedin.com/blog/2017/11/dali-views--functions-as-a-service-for-big-data). Consumers move to the new version when they choose, before a deprecation date, which dbt's [model versions](https://docs.getdbt.com/docs/mesh/govern/model-versions) record as a `deprecation_date` on each version.

Versioning matters more for features, because a model learns the meaning of each input during training. Sculley and colleagues wrote in 2015 that ["One common mitigation strategy for unstable data dependencies is to create a versioned copy of a given signal"](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf). Chronon, the feature platform that Airbnb open-sourced and Stripe adopted, enforces the practice in its compiler, and its documentation states that ["Once a groupBy is marked online, the compiler compile.py will prevent you from updating it"](https://chronon.ai/authoring_features/GroupBy.html) and recommends creating a `_v2` instead. Embeddings are the extreme case, because values produced by two versions of an embedding model should not be mixed, and Hopsworks gives a changed embedding algorithm as its example of a change that needs [a new version and a backfill](https://docs.hopsworks.ai/latest/concepts/fs/feature_group/versioning/).

Each model is then bound to the exact versions of the data and features it was trained on. Feast's [design note on feature versioning](https://feast.dev/blog/feature-view-versioning) starts from a model A that uses v1 features and a model B that uses v2 features. It rejects a shared table with a version column because "a model trained against v1 of a feature must retrieve v1 rows, not v2 rows that happen to occupy the same table".

A schema registry, a dbt contract or a compiler check will catch a renamed column or a changed type. None of them detects a semantic change, in which the type stays the same and the meaning moves, so the author of such a change has to declare it as a new version. LinkedIn's example is [a time field that changes from seconds to milliseconds](https://engineering.linkedin.com/blog/2017/11/dali-views--functions-as-a-service-for-big-data), and dbt's guidance lists [changes to the logic, granularity or filters behind a metric](https://docs.getdbt.com/best-practices/how-we-mesh/mesh-6-coordinate-versions) as changes that may break consumers and that its contracts do not catch. Nubank wrote that "we rarely run into issues due to upstream data schema changes breaking analysis downstream", and [described changes to upstream data values as the harder problem](https://building.nubank.com/microservices-at-nubank-an-overview/).

A new version is needed only where some consumers must keep the old meaning while others move. An added column changes nothing for existing readers, and a bug fix is a change that every consumer should receive at once, so both can be published in place once the checks on the new data pass. [SQLMesh](https://sqlmesh.readthedocs.io/en/stable/concepts/plans/) records this decision for each changed model as breaking, non-breaking or forward-only, and infers it for the models downstream. A forward-only change applies the new logic only to data processed from then on, which avoids rebuilding history at the cost of a break in the series that consumers have to be told about.

The [2015 paper](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf) also named the running cost of versioning: "potential staleness and the cost to maintain multiple versions of the same signal over time." Old versions accumulate in the same way as stale feature flags, because removal waits for the last consumer and is done by hand, and Feast's design record notes that it has [no mechanism to prune old versions](https://docs.feast.dev/project/adr/adr-0008-feature-view-versioning). A v2 chain built beside a v1 chain also doubles the compute and storage of every table in it until the v1 deprecation date.

## Two versions of a column or table

Keeping two versions of one column in an operational database is the most thoroughly documented case. Ambler and Sadalage described it in 2006 as a transition period during which the database supports both schemas, and warned that "Typical transition periods last for several quarters, if not years" when several applications share the database ([Red Gate excerpt](https://www.red-gate.com/simple-talk/databases/sql-server/database-administration-sql-server/refactoring-databases-the-process/)). When one team owns every reader of the database, the transition can be much shorter.

The right tool for a schema change depends on whether the obstacle is physical or logical. Rewriting a large table without locking it is a physical problem, which online schema-change tools such as [GitHub's](https://github.blog/news-insights/company-news/gh-ost-github-s-online-migration-tool-for-mysql/) gh-ost handle. Keeping old and new code correct against the same data is a logical problem, and it requires every read and write to pass through one place where a flag can choose the target. [Figma](https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/) created Postgres views for each future shard on its still unsharded database and routed reads and writes through them with flags and percentage rollouts. Before any data had moved, it could therefore roll back "within seconds by just rerouting traffic back to the main table".

Published migrations of this kind follow much the same sequence of steps. The figure below shows, for each step, which copy is written, which is read and which is authoritative.

![Seven steps for running two copies of a column or table, showing for each step which copy is written, read and authoritative. The old copy stays authoritative through expand, keep both populated, backfill, compare reads and switch reads; a flag may gate writes to the new copy, and later a flag or percentage moves reads to it. At step 6 a flag chooses the authoritative store, the new copy becomes authoritative, and changes are copied back to the old copy so that rollback stays possible. At contract, writes to the old copy stop and it is deleted after enough releases.](figures/22-two-copies.svg)

1. Expand. Add the new column or table beside the old one, where existing code ignores it.
2. Keep both copies populated, with a database trigger, with application writes to both that a flag or percentage controls, or by replaying a change log. [Stripe](https://stripe.com/blog/online-migrations) raised the share of objects written to both stores gradually while watching operational metrics.
3. Backfill historical rows, throttled against the health of the database. Notion's backfill took about three days and Discord's nine.
4. Compare reads from both copies while still returning the old result. Notion called these dark reads and accepted the added API latency for "confidence that the switch-over would be seamless."
5. Switch reads by flag or percentage. LinkedIn moved reads one customer at a time.
6. Make the new copy authoritative for writes, and keep copying changes back to the old copy if rollback is to remain possible.
7. Contract. Stop writing the old column and delete it once enough releases have passed. [GitLab](https://docs.gitlab.com/development/database/avoiding_downtime_in_migrations/) spreads a drop over three releases, partly because "dropping a column is a destructive operation that can't be rolled back easily", and Uber kept its old ledger store for about a month after writes to it stopped.

The flag that chooses the authoritative store needs stronger guarantees than an ordinary feature flag. [Noah](https://noah.com/blog/zero-downtime-migration-of-noahs-internal-ledger) moved its ledger between two databases behind boolean flags, and because of caching and deployment timing, "different parts of the system occasionally had conflicting views of which ledger was active". Noah replaced the flag with a timestamp set in the future, at which every service switched together. [Stripe's](https://stripe.com/blog/how-stripes-document-databases-supported-99.999-uptime-with-zero-downtime-data-migrations) document-database platform switches with a routing token and keeps replication running in both directions, and reports that "The entire traffic switch protocol takes less than two seconds to execute". [GitHub](https://github.blog/engineering/infrastructure/partitioning-githubs-relational-databases-scale/) pauses writes for a few tens of milliseconds, and Notion and LinkedIn used scheduled maintenance windows.

Request-by-request comparison is used only for reads, because a candidate that wrote to the same database would change the data that the production code path reads. [Uber](https://www.uber.com/blog/schemaless-rewrite/) validated its read endpoints by running both implementations, covered writes with tests, and then moved write traffic by percentage.

The migration machinery can itself cause an outage or nearly overwrite good data, and some migrations cannot practically be reversed. On November 27, 2021, the final rename step of a schema migration on a large table put a significant portion of [GitHub's](https://github.blog/news-insights/company-news/github-availability-report-november-2021/) read replicas into deadlock and crash recovery, and core services were unavailable for 2 hours 50 minutes. [GoCardless](https://gocardless.com/blog/zero-downtime-postgres-migrations-the-hard-parts/) took "around 15 seconds of unexpected API downtime" during a planned migration when a foreign-key lock queued behind a long-running read. [Aircall's](https://aircall.io/en-gb/blog/tech-team-stories/elasticsearch-to-opensearch/) backfill tool reported zero failures for a run that "would have silently overwritten 13.5M newer documents with stale copies". At [LinkedIn](https://engineering.linkedin.com/blog/2021/new-recruiter---jobs--the-largest-enterprise-data-migration-at-l) the old and new data models did not map one to one, so "it is not practical to go back and forth between the two systems".

## Changing a table that has downstream dependents

Before a shared table changes, its owner needs a list of everything that reads it, including consumers that a lineage tool cannot see, such as notebooks, exports and feature pipelines in another system. [LinkedIn](https://engineering.linkedin.com/blog/2021/evolving-linkedin-s-analytics-tech-stack) built lineage and usage pipelines before a warehouse migration and used them to cut its scope from 1,424 datasets to 450, after an earlier attempt had left both warehouses running with "double the maintenance cost and complexity, along with very confused consumers".

The new version of each table is then written where consumers cannot see it, checked, and only afterward made visible, a pattern known as write-audit-publish. Netflix presented it in a 2017 talk, ["Whoops, The Numbers Are Wrong! Scaling Data Quality @ Netflix"](https://www.slideshare.net/slideshow/whoops-the-numbers-are-wrong-scaling-data-quality-netflix/77278406). Ryan Blue of Netflix [built support for it into Apache Iceberg](https://github.com/apache/iceberg/pull/342) in 2019, and by 2023 [Netflix's workflow scheduler](https://netflixtechblog.com/incremental-processing-using-netflix-maestro-and-apache-iceberg-b8ba072ddeeb) offered it as a template. [Lyft](https://eng.lyft.com/from-big-data-to-better-data-ensuring-data-quality-with-verity-a996b49343f6) built its own version, which stages data and promotes it only after a blocking check, after bad data "caused tainted experimentation metrics, inaccurate machine learning features, and flawed executive dashboards".

On [Iceberg](https://iceberg.apache.org/docs/latest/branching/) the audit can run on a branch and publishing moves a pointer; on open-source [Delta Lake](https://docs.delta.io/latest/delta-utility.html) the documented route is a staging table or shallow clone, the checks, and a write back into production. For a chain of tables, as in the figure below, each v2 table is checked on its own and one commit can then make all of them visible together. [Databricks](https://docs.databricks.com/aws/en/transactions/) supports this as a transaction across many tables that aborts if a final check fails, but a table restore cannot run inside such a transaction, so rollback after a joint publish still proceeds table by table.

![Write, audit, publish for a chain of three tables. The v2 tables are written in a staging area that consumers cannot see, and each is checked there. One commit then publishes all the v2 tables together and aborts if a final check fails. The v1 tables stay readable throughout, and consumers cut over from v1 to v2 one at a time, before the v1 deprecation date. Publishing several tables in one commit follows Databricks documentation.](figures/23-write-audit-publish.svg)

The v2 chain is then built beside the v1 chain and the outputs are compared. In [Meta's ingestion migration](https://engineering.fb.com/2026/05/12/data-infrastructure/migrating-data-ingestion-systems-at-meta-scale/), the new jobs first read the same source as the old ones and wrote to shadow tables, and the team compared row counts and checksums, landing latency and resource use. In a second phase, which Meta calls reverse shadow, the new job wrote the production table and the old job wrote the shadow table, so comparison continued and rollback did not require the old job to be recreated. Both systems ingested by change data capture, which generates each new load from data already landed, so a problem in landed data would pass into every load generated after it.

A v2 table cannot replace v1 until its history has been rebuilt, and in a chain the rebuilds run in dependency order. [Airbnb](https://medium.com/airbnb-engineering/airbnb-metric-computation-with-minerva-part-2-9afe6695b486) splits two years of history into 24 monthly batches that run in parallel, and wrote that "In practice, backfills often could not catch up with user changes, especially when updates affect many datasets". [Netflix](https://netflixtechblog.com/incremental-processing-using-netflix-maestro-and-apache-iceberg-b8ba072ddeeb) reports that reprocessing a lookback window for late data multiplies the cost by almost the number of days in the window.

Consumers then cut over one at a time, before the v1 deprecation date. Streaming consumers need particular care, because a plain Delta streaming source accepts only appends: "Structured Streaming does not handle input that is not an append and throws an exception if any modifications occur on the table being used as a source" ([Delta Lake](https://docs.delta.io/latest/delta-streaming.html)).

## Event streams

A schema registry rejects a new event schema that breaks the topic's compatibility mode, and the mode decides whether producers or consumers upgrade first.

| Mode | Who upgrades first | Note |
| --- | --- | --- |
| BACKWARD, the default | Consumers: [Confluent's documentation](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html) says to "upgrade all consumers before you start producing new events" | Checks a new version only against the one before it, so a consumer that replays a long-retention topic from the start would need the transitive form of the mode |
| FORWARD | Producers | |
| FULL | Either, independently | |
| BACKWARD or a mode that includes it, for Kafka Streams applications | The applications, because their state and changelog topics still hold old-schema data: ["The Kafka Streams apps must be upgraded first, then it's safe to upgrade the upstream producer"](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html) | Kafka Streams supports only modes that include backward compatibility |

Under BACKWARD compatibility a producer can return to the schema it used before, because upgraded consumers can still read old-schema events. A consumer cannot return to its old schema once producers write the new one, since the mode guarantees old readers nothing about new data. A team that wants to roll producers and consumers back independently therefore needs FULL compatibility.

Event pipelines either forbid a breaking change or move it to a new topic. [Shopify](https://shopify.engineering/capturing-every-change-shopify-sharded-monolith) avoids breaking schema changes wherever it can, and [LinkedIn's](http://sites.computer.org/debull/A12june/pipeline.pdf) 2012 pipeline allowed only additive changes with a default value for each new field. [Yelp's](https://engineeringblog.yelp.com/2016/08/more-than-just-a-schema-store.html) rule is that "Only compatible schemas can use the same topic", so registering an incompatible schema creates a new topic automatically, and consumers move to it on their own timeline. Each consumer then has to switch topics without skipping events or processing them twice, which [Confluent](https://docs.confluent.io/platform/current/schema-registry/fundamentals/data-contracts.html) describes as complex.

To change the logic of a stream job, Jay Kreps [proposed in 2014](https://www.oreilly.com/radar/questioning-the-lambda-architecture/) to "start a second instance of your stream processing job that starts processing from the beginning of the retained data" and write its output to a new table. The application switches to that table once the second job has caught up, and the old job is then stopped and the old table deleted. While both tables exist, reverting the change means pointing the application back at the old one. Kreps added that for important changes "you can control the cut-over with an automatic A/B test or bandit algorithm".

![Jay Kreps's 2014 procedure for changing the logic of a stream job. Job v1, with the current logic, writes table v1 from the log. A second instance, job v2, runs the new logic from the beginning of the retained data and writes table v2. The application reads table v1 until job v2 has caught up, then reads table v2; while both tables exist, pointing it back at table v1 reverts the change. The old job is then stopped and the old table deleted.](figures/24-stream-rebuild.svg)

A second job can rebuild only what the log still holds. In 2021 Uber kept Kafka data for only a few days, and its engineers [wrote](https://arxiv.org/pdf/2104.00087) that "Therefore, we're unable to adopt the Kappa architecture", so it ran the same streaming code against archived Hive data instead. Kafka's [tiered storage](https://cwiki.apache.org/confluence/display/KAFKA/KIP-405%3A+Kafka+Tiered+Storage), production-ready since 2024, moves older log segments to object storage, which lowers the cost of keeping a year of history in the log itself, although it does not support compacted topics. [Wise](https://developer.confluent.io/podcast/running-hundreds-of-stream-processing-applications-with-apache-kafka-at-wise) keeps its original event streams in compacted topics so that a new version of a job can consume, for example, a year of data, although [compaction keeps only the latest value for each key](https://github.com/apache/kafka/blob/trunk/docs/design/design.md).

Job state limits what can change in place, because [Flink](https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/upgrading/) cannot evolve the schema of keys, and changing the input or output type of a window, join or aggregation prevents an upgrade. A principal engineer at [Wise](https://developer.confluent.io/podcast/running-hundreds-of-stream-processing-applications-with-apache-kafka-at-wise) said in 2021 that "in the Kafka Streams right now, there is no way to roll back your state in a consistent manner". [Grab](https://engineering.grab.com/enchancing-flink-shadow-testing) built an automated shadow stage for its Flink jobs because new versions sometimes could not resume from the old version's savepoint, and its deployment system rolled back such a failure only after ten minutes of observation, leaving the application down for about that long. The new version consumes a full copy of the stream, writes to a separate shadow cluster and is judged on job health.

Change data capture publishes a table's changes as events, which makes the table's schema the event schema. Gunnar Morling, formerly Debezium's lead, [summarized the risk](https://www.morling.dev/blog/change-data-capture-breaks-encapsulation-does-it-though) as "Your table model becomes your API", and described an outbox table, written in the same database transaction as the business change, whose event contract evolves separately from the table. Without an outbox or a contracted republishing job, each step of an expand-and-contract change to a source column would reach every stream consumer.

Rolling back a producer or a stream job changes only the events written afterward. A compacted topic keeps a bad value for a key until a newer value replaces it, and [Kafka's](https://github.com/apache/kafka/blob/trunk/docs/design/design.md) transactions give exactly-once processing only within Kafka. Events that a consumer cannot process also stay in the log. [Monzo](https://monzo.com/blog/how-we-built-a-queue-on-top-of-kafka), which writes that "it's only a matter of time before a partition contains a poison pill", moves events that keep failing to a dead-letter topic for each consumer group and replays them after the fix.

## Feature stores

A feature store holds the inputs that models read, computed offline for training and served online at decision time, and versioning a feature there also requires point-in-time correctness and agreement between the offline and online values. [Point-in-time correctness](https://chronon.ai/authoring_features/Join.html) means that a training row may use only events that preceded its timestamp. Databricks notes that the point-in-time functionality of its feature store ["is not related to Delta Lake time travel"](https://docs.databricks.com/aws/en/machine-learning/feature-store/time-series), so a v2 feature needs its history backfilled under the v2 logic before any model can be trained on it.

Agreement between online and offline values [failed at Google Play](https://stevenwhang.com/tfx_paper.pdf), where some features were always missing from serving logs and always present in training. An A/B experiment showed that removing this skew raised the install rate on the store's main landing page by 2%. [Chronon](https://chronon.ai/test_deploy_serve/Online_Offline_Consistency.html) measures the gap by logging a sample of online requests and responses, recomputing the same features offline and reporting a mismatch rate, with the caveat that "While 100% consistency is desirable, it is not always possible". [Stripe](https://stripe.com/blog/shepherd-how-stripe-adapted-chronon-to-scale-ml-feature-development) integrated this monitoring for a SEPA fraud model with more than 200 features. The same check would allow a v2 feature to be materialized online with no model reading it and compared with its backfill, which is the feature-store equivalent of a shadow run, although no one has described doing so.

The alternative to a backfill is to log feature values at serving time and train on the logs. Google's [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml) recommends this as Rule #29 and reports that the YouTube home page switched to it with significant quality improvements, and [Uber](https://www.uber.com/blog/taming-ml-firehose/) Eats built a new training table from logged features beside its older ETL table. Logging removes skew by construction and costs calendar time, since a model cannot be trained until [enough history has accumulated](https://raw.githubusercontent.com/airbnb/chronon/main/README.md). A 90-day streaming aggregate needs 90 days of history before its v2 can be trusted. Unless the topic retains that much history, it has to come from an archive and a batch backfill, which brings back the second code path.

![Two routes to the history a v2 feature needs before a model can be trained on it. Backfill: history from an archive is recomputed in a batch backfill under the v2 logic with point-in-time joins, and the offline values are compared with those served online and a mismatch rate reported; the backfill is a second code path. Logging: the v2 feature is computed at serving time and its values are logged; training data then matches what was served, but no model can be trained until the history has accumulated, and a 90-day aggregate needs 90 days of logs.](figures/25-feature-history.svg)

The binding between a model and its feature versions is held in the model's configuration or artifact. [Databricks](https://docs.databricks.com/aws/en/machine-learning/feature-store/train-models-with-feature-store) binds a logged model to table and feature names and documents no parameter for a table version, so v1 and v2 must exist as separate tables or views for as long as either model serves. [Uber](https://content.hopsworks.ai/hubfs/Feature%20Store%20Summit%202022/FS%20Summit%2022%20-%20Uber.pdf) allows a feature to be removed only when no model references it, and [DoorDash waits](https://www.infoq.com/presentations/fabricator-ml) until a feature's usage has been zero for about 30 days.

## Releasing models

Model releases at Uber, Monzo and Nubank begin with shadow scoring. [Uber's](https://www.uber.com/blog/continuous-integration-deployment-ml/) prediction service runs shadow models on all or part of the primary model's traffic, usually for days or weeks, and fetches for them only the features the primary model does not already use. [Monzo](https://monzo.com/blog/2022/04/26/monzos-machine-learning-stack) writes that "we use shadow mode deployments extensively". Its former machine-learning lead [gives fraud monitoring](https://nlathia.github.io/2020/07/Shadow-mode-deployments.html), where volume is low and the impact of a mistake is high, as a case in which a team may not want to send a share of traffic down an untried path. Nubank [runs its fraud models in shadow](https://building.nu.com/practices-to-scale-machine-learning-operations/) and [advises](https://building.nu.com/de-risking-real-time-ml-projects-addressing-common-failure-modes/) "Deploy the model in shadow mode as early as possible".

The flag or experiment selects a model, and the features follow from that model's configuration. [LinkedIn's](https://www.linkedin.com/blog/engineering/machine-learning/scaling-machine-learning-productivity-at-linkedin) model registry records each artifact's dependencies on code and features, checks automatically "are all the features available both offline and online?", and is tied to the experimentation platform so that every active experiment has the artifacts it needs.

[Booking.com published a design](https://doi.org/10.1145/3292500.3330744), shown in the figure below, that keeps a live comparison of two models fair. Its control group "invokes and uses the output from model 1, the current baseline, and also works as a safety net". In both treatment arms "the outputs from both models are required", and each arm acts on one of them, so the two treatments carry the same computational load and latency drops out as a confounder. The analysis covers only the subjects for whom the models disagree.

![Booking.com's three-arm test of two models. The control arm computes only model 1, the baseline and safety net, and uses its output. Treatment 1 and treatment 2 both compute model 1 and model 2, so they carry the same computational load; treatment 1 uses model 1 and treatment 2 uses model 2. Only the subjects for whom the two models disagree are compared, and computing both models doubles inference and feature-fetching cost in the treatment arms.](figures/26-three-arm-test.svg)

[Adyen](https://www.adyen.com/knowledge-hub/the-ai-behind-uplift) names the stages of a model's life ghost, challenger, principal and retired, where a ghost is a model for which "we only log telemetries and statistics but we do not influence outcomes". Every model runs on an experimentation service that compares several arms against one shared control group, which still receives a market baseline such as blocking cards known to be stolen, and a challenger replaces the principal when it performs better with statistical confidence.

Google's [ML Test Score](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/46555.pdf) counts among its production-readiness tests that an automated system "must either bless the model or veto it" before the model affects real traffic, that models pass through a canary, and that "Models can be quickly and safely rolled back to a previous serving version". [Uber's](https://www.uber.com/blog/raising-the-bar-on-ml-model-deployment-safety/) deployments roll back automatically to the last known good version when error rates, latency or utilization breach thresholds. These rollbacks respond to a broken model. None of these companies describes rolling back automatically on business outcomes, so the judgment that a model performs worse rests with people reading experiment results.

For one of [Booking.com's](https://doi.org/10.1145/3292500.3330744) models, the label those results depend on arrives after the guest's stay, "which can be months later". A fraud model also hides the outcome of its own decisions, since, as [Stripe](https://stripe.com/guides/primer-on-machine-learning-for-fraud-protection) writes, payments its model scores above the threshold "are blocked, and so we can't know what their outcomes would have been", and [Adyen](https://www.adyen.com/knowledge-hub/the-ai-behind-uplift) says the same of transactions it blocks for fraud. A deployed model therefore shapes the data its successor trains on, a loop that [Bottou and colleagues analyzed](https://jmlr.org/papers/v14/bottou13a.html), and reverting a bad model still leaves a training set labeled only where that model let outcomes be seen. Stripe's guide adds that measuring a model in production needs counterfactual estimates of what would have happened to the payments it blocked. Bottou and colleagues obtain such estimates by randomizing a small share of decisions, so a team that intends to compare fraud models on live outcomes would need that randomization in place before the comparison starts.

Live tests lose power as models improve, because the rate at which a model and its successor disagree falls, and the exposed population with it. Nor can offline evaluation stand in for them, since [Booking.com](https://doi.org/10.1145/3292500.3330744) concluded that "Offline model performance metrics are only a health check" after finding, across 23 comparisons involving 46 models, that offline gains correlated with business gains at a Pearson coefficient of -0.1, with a 90% confidence interval from -0.45 to 0.27.

## Worked example: from a source table to two models

Suppose a payment company's `transactions` table stores each merchant's category as free text, and the company replaces it with a merchant identifier and a category from a proper code set. Ten lakehouse tables are derived from `transactions`, a fraud feature called `merchant_risk_30d` is computed from the last of them, and the fraud model in production, model A, uses that feature. A new model, B, is to be trained on features computed from the new category, and the company wants to test it against model A on live traffic. The figure below shows the steps in order. No company has published the whole sequence, although companies have described most of its steps separately; the holds and caps in the feature, shadow, experiment and ramp steps are the author's.

![A swimlane of the worked example's eleven steps, with lanes for the transactions table, the ten derived tables, the feature store, model A and model B. The new columns are added to the transactions table. In the derived tables lane, the team finds who reads the ten tables, builds and backfills a v2 of each, and checks each before publishing; publishing all ten together rests partly on vendor documentation. The v2 feature is added to the feature store with no model reading it. Model B is trained and model A retrained on the same dates, model B and the retrained model A are shadowed, the three-arm experiment runs, and model B is ramped up with model A as the fallback. Finally model A is retired and the old chain is removed from the feature store, the derived tables and the transactions table. The feature, shadow, experiment and ramp steps include a hold or limit set by the author.](figures/27-worked-example.svg)

Model A is retrained on the old data over the same dates as model B, so that the training window is the same and the experiment measures only the change in data, which is how [Uber Eats](https://www.uber.com/blog/taming-ml-firehose/) compared an old table with a new one. The retrained model A is itself a new model, so it would be shadowed beside model B before it serves as the baseline in the experiment. The experiment is capped in size because a challenger that lets more fraud through raises the company's overall fraud rate. If the company is itself the provider that exempts low-risk transactions from strong customer authentication, as a card issuer or an acquirer may be, that rate decides under the PSD2 standard whether it may exempt them for any customer ([model and data rules](appendices.md#model-and-data-rules)). Rollback stays cheap only while the v1 chain is still running, and even then it cannot undo the decisions model B made while it was live, such as a payment it declined. Model A reads the v1 feature for as long as it serves as the fallback, so the v1 chain can be removed only after model A has been retired.

## Ownership of shared data

Versioned tables, write-audit-publish and consumer cut-over all depend on someone knowing who reads a table and someone having the authority to change it. Google's [Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml) asks teams to "Give feature columns owners and documentation".

A data contract or a mandatory owner puts the producer of a dataset under an obligation to the teams that read it, and the companies that have published their rules differ in what a change to a shared dataset requires.

| Company | What a change requires |
| --- | --- |
| GoCardless | Contracts, introduced by Andrew Jones in 2021, provision BigQuery and Pub/Sub resources when merged, with a change process that "is intentionally heavy" ([post on the blog of the monitoring vendor Monte Carlo](https://www.montecarlodata.com/blog-data-contracts/)) |
| [Adevinta](https://adevinta.com/techblog/creating-source-aligned-data-products-in-adevinta-spain/) Spain | "For any change, including schema changes, whether minor or major, a new contract version should be created"; automating pipelines from the contracts cut time to usable data from about five days to about 30 minutes |
| [Monzo](https://monzo.com/blog/a-meshy-approach-to-data) | More than 100 teams contribute to more than 12,000 dbt models. After finding that "A schema change here broke downstream models there.", Monzo made selected models interfaces, which a team declares as governed contracts for other teams, and enforces an explicit owner team and freshness tests on every pull request |
| [Uber](https://www.uber.com/blog/ubers-journey-toward-better-data-culture-from-first-principles/) | Ownership is mandatory where it cannot be inferred, and reviewers are mandatory for schema changes; producers and consumers of mobile analytics events can add themselves as reviewers |
| [Nubank](https://building.nubank.com/scaling-data-analytics-with-software-engineering-best-practices/) | Each dataset's owner is recorded in structured metadata, and integration tests must pass before a table is published or changed; tables that feed models are in a stricter class with different expectations about who validates changes |

[LinkedIn](https://engineering.linkedin.com/blog/2021/evolving-linkedin-s-analytics-tech-stack) deprecated datasets by identifying those with no dependencies and low usage, emailing their users, and locking, archiving and deleting them after a grace period. On-call for data takes the form of alerts routed to owners and subscribers, and [LinkedIn's](https://engineering.linkedin.com/blog/2022/towards-data-quality-management-at-linkedin) Data Health Monitor watches about 150,000 critical datasets, gained more than 2,000 consumer subscriptions within several months, sends an email alert roughly 30 minutes after it detects a problem, and names email alert fatigue as a problem.

Monzo's interfaces and LinkedIn's Super Tables suggest that changes inside a team can stay small and frequent while the interface between teams is versioned and paced for its consumers, with the producer bearing the cost of the slower cadence. LinkedIn's 2022 post on Super Tables starts from the observation that "Changes to the datasets or their sources are usually made without consulting with or even notifying all downstream consumers", and for its most widely shared tables [LinkedIn](https://engineering.linkedin.com/blog/2022/super-tables--the-road-to-building-reliable-and-discoverable-dat) put changes on a fixed schedule. It adopted "committed change velocity (e.g., monthly deployment of changes)", a governing body that includes producers and consumers, an availability target above 99%, and a migration guide for the dozen tables and views each Super Table replaces.

No published source measures a reduction in incidents after contracts or mandatory ownership were introduced. The outcomes that were measured are delivery speed at Adevinta, alert latency at LinkedIn and detection coverage at [Uber](https://www.uber.com/blog/operational-excellence-data-quality/).

## Regulation of data and model changes

Model-risk rules in the United States, the United Kingdom and the EU expect a model to be validated before it is used, and European supervisors treat a shadow run that takes no decisions as expected, or as good practice, before sign-off. A live challenger arm makes decisions, so it counts as use and [needs validation before it starts](appendices.md#model-and-data-rules). Capital models carry notification rules of their own.

## What a data team should change

- A change to the meaning of a column, feature or event gets a new name, and the old version gets a deprecation date. Added columns and bug fixes that every consumer should receive are published in place.
- Shared tables are published only after checks on staged data pass, starting with the tables that feed models, financial reporting and files sent outside the company.
- Feature definitions that a model reads online cannot be edited, and each model is bound to the feature versions it was trained on.
- Every decision is logged with the model version and the feature versions it read.
- Every model runs in shadow before it acts. Where a model's own decisions hide outcomes, a small randomized share of decisions keeps those outcomes measurable.
- The v1 tables, the old topic and the old model stay until their last consumer has moved, and their removal is tracked with the same owner and date as a stale flag.
