## 1. Feature versioning and immutability: what is the rule for changing a feature?

### Takeaway

Across every platform whose documentation or first-person account I could read, the rule for a change that alters a feature's values or schema is the same: do not edit a feature that a live model reads; publish a new named or numbered version (`your_gb_v2`, `my_feature_view:v2`, feature group version 2), backfill it, and leave the old one running. The platforms differ in how hard they enforce this: Chronon's compiler refuses the edit, Tecton deletes and rematerialises (with downtime) unless you rename, Hopsworks requires a version bump for "breaking" changes, and Feast had no first-class versioning at all until an experimental release in March 2026.

### Cited Findings

**Chronon (Airbnb; open-source docs) — FULL-TEXT:**

- Source: The Chronon Authors (Airbnb/Stripe), "GroupBy" documentation, section "Online/Offline Toggle"; undated living docs, read 2026-11-11. Once a feature group (GroupBy) is marked `online=True`, the compiler blocks changes to it. Exact wording: "Once a groupBy is marked online, the compiler compile.py will prevent you from updating it." The stated reason: "so that you don't accidentally merge a change that release modified features out-of-band with model updates." The recommendation: "Our recommendation is to create a new version your_gb_v2 instead." The lock can be overridden "by deleting the older compiled output." — [Chronon docs, GroupBy](https://chronon.ai/authoring_features/GroupBy.html)
  - Limits: documentation of the open-source tool; does not say how often Airbnb or Stripe engineers override the lock, how many `_v2` groups exist, or when old versions are retired.
- Same docs, naming convention: every example object carries a version suffix in its name (`purchases_v1`, `returns_v1`, join output table `my_team_my_join_v1`, feature columns such as `quickstart_purchases_v1_purchase_price_sum_3d`), so the version is part of the feature's identity in both the offline table and the online key. — [Chronon docs, Join](https://chronon.ai/authoring_features/Join.html)
  - Limits: a naming convention, not a version-management system; there is no registry concept of "v1 supersedes v2" in the pages I read.

**Tecton (VENDOR documentation, v1.2) — FULL-TEXT:**

- Source: Tecton, Inc., "Feature Services" docs page, section "Update a Feature Service"; read 2026-11-11. Exact wording: "Tecton objects are immutable. To change the features in a Feature Service, create a new one (e.g., fraud_detection_v3) with the updated list of features." — [Tecton docs, Feature Services](https://docs.tecton.ai/docs/reading-feature-data/feature-services)
- Source: Tecton, "Production Best Practices", section "Use Variants when Updating Feature Views and Services". Exact wording: "Use a variant naming convention when modifying production Feature Views and Feature Services." The variant is a suffix on the name, e.g. `name="my_feature_view:v2"` or `my_feature_service:v2`; Tecton then creates new objects under the variant name. — [Tecton docs, Production Best Practices](https://docs.tecton.ai/docs/running-in-production/production-best-practices)
- Source: Tecton, "Use prevent_destroy to Protect Production Pipelines and Services". What happens if you edit in place instead: changing the SQL of a Feature View causes a "recreate"; "Recreates are destructive"; Tecton rematerialises the tables and cleans up the old ones, and "During this time, those Feature Views will not be available for online serving." Also: "destructive changes cascade to dependent objects". — [Tecton docs, prevent_destroy](https://docs.tecton.ai/docs/running-in-production/prevent_destroy)
- Source: Tecton, "Suppress Recreates" (under "Optimize Costs"). Recreating a materialised Feature View "deletes any materialized data, and re-runs the backfill process from the feature start time. This process, called re-materialization, incurs cost and downtime." The `--suppress-recreates` escape hatch is allowed only when "the upstream and downstream contracts of a feature pipeline are unchanged" (refactoring, upstream data-source migrations). It cannot be used for "Modification of the schema (such as adding a column or removing a column) of a Data Source or Feature View", some stream window-aggregate changes that "would invalidate the checkpoint", or "Increasing the ttl". — [Tecton docs, Suppress Recreates](https://docs.tecton.ai/docs/manage-costs/suppress-recreates)
  - Limits (all Tecton items): vendor documentation describing mechanism; no customer numbers on cost, duration or frequency.

**Hopsworks (VENDOR documentation) — FULL-TEXT:**

- Source: Hopsworks AB, "Versioning" concept page; read 2026-11-11. Explicit breaking/non-breaking rule. Exact wording: "If you make a breaking change to the schema of a feature group, you need to increment the version of the feature group, and then backfill the new feature group." A breaking change is: dropping a column; adding a feature "without any default value"; or changing "how a feature is computed" so old and new data are incompatible for training. The page's own example is an embedding whose algorithm changes: do not mix values from the old and new embedding model. — [Hopsworks docs, Versioning](https://docs.hopsworks.ai/latest/concepts/fs/feature_group/versioning/)
- Same page: feature views (the model-facing interface) are versioned separately; a change of feature types or transformations requires a new feature view version "to prevent breaking existing clients." Training datasets are numbered under a feature view version. Deployments are the one unversioned asset: "upgrades and rollbacks are done with blue/green deployments". — [Hopsworks docs, Versioning](https://docs.hopsworks.ai/latest/concepts/fs/feature_group/versioning/)
- Source: Hopsworks, "Deprecate" user guide. Old feature groups can be marked deprecated; users are "warned when they try to use it or use a feature view that depends on it." — [Hopsworks docs, Deprecate](https://docs.hopsworks.ai/latest/user_guides/fs/feature_group/deprecation/)
  - Limits: vendor docs; a warning is not enforcement; nothing on automatic garbage collection.

**Feast (open source, originally Gojek/Google) — FULL-TEXT:**

- Source: Feast maintainers, "Feast Introduces Experimental Feature View Versioning", blog, 31 March 2026 (outside the 2015-2025 window but it documents the state before it). Before this release there was "no first-class way" to manage competing versions "without creating separate feature views with different names and hoping teams don't collide." The post calls versioning "a long-requested capability". — [Feast blog](https://feast.dev/blog/feature-view-versioning)
- Source: Feast, "ADR-0008: Feature View Versioning" (same period). Context section lists the prior problems: "No safe rollback" and "No multi-version serving", the latter worked around by "creating entirely separate feature views." New rule: only schema and UDF changes create a version; description, tags, owner and TTL changes "update the active definition in place". — [Feast ADR-0008](https://docs.feast.dev/project/adr/adr-0008-feature-view-versioning)
  - Limits: project documentation; the feature is alpha/experimental and SQLite-only (see section 6).

**Amazon SageMaker Feature Store (VENDOR documentation) — FULL-TEXT:**

- Source: AWS, "Add features and records to a feature group". Schema evolution is add-only: "After you successfully add features to a feature group, you cannot remove those features." Newly added features "do not add any data to your records" (no automatic backfill). — [AWS SageMaker docs](https://docs.aws.amazon.com/sagemaker/latest/dg/feature-store-update-feature-group.html)
  - Limits: says nothing about changing a feature's computation; by implication that needs a new feature name or group.

**Google Vertex AI Feature Store (VENDOR documentation) — FULL-TEXT:**

- Source: Google Cloud, Feature Store overview, "Resource version metadata". Exact wording as rendered on the page in Nov 2026: "Agent Platform Feature Store only supports the version 0 for features." i.e. there is no built-in multi-version feature resource; versioning must be done by naming. — [Google Cloud docs](https://cloud.google.com/vertex-ai/docs/featurestore/latest/overview)
  - Limits: one sentence of product documentation; product was renamed and the page has changed over time.

**Feathr (LinkedIn open source) — FULL-TEXT:**

- Source: Feathr project docs, "Feature Registry and Feathr UI". Re-registering a changed feature under an existing name is unsupported: "it will be treated as updating an exsiting project which is not supported by feathr and will cause errors." [sic] — [Feathr registry doc (GitHub raw)](https://raw.githubusercontent.com/feathr-ai/feathr/main/docs/concepts/feature-registry.md)
- Source: David Stein (LinkedIn), "Open sourcing Feathr – LinkedIn's feature store for productive machine learning", LinkedIn Engineering blog, 12 April 2022 (date from memory of the post; the text I read did not show it clearly — verify). Feathr is deployed for "dozens of applications" and "hundreds of model workflows"; adding features went "from weeks to days". Versioned upgrade testing is described as future work: "users will be able to create upgraded versions of widely-shared ML features that will then be automatically tested against existing models". — [LinkedIn Engineering](https://engineering.linkedin.com/blog/2022/open-sourcing-feathr---linkedin-s-feature-store-for-productive-m)
  - Limits: the post describes the upgrade-and-test workflow as something being built in 2022, not as shipped; I found no later first-person LinkedIn account of it.

**Uber Michelangelo / Palette:**

- Source: Jeremy Hermann and Mike Del Balso (Uber), "Meet Michelangelo: Uber's Machine Learning Platform", 5 Sept 2017 — TOOL-EXTRACT. Models consume shared features by "canonical name" in the model configuration; about 10,000 features in the store in 2017; batch features recomputed daily. The post does not describe feature versioning. — [Uber blog](https://www.uber.com/blog/michelangelo-machine-learning-platform/)
- Source: Uber, Feature Store Summit 2022 slide deck (Palette) — FULL-TEXT of slide text. Slide "Feature Sharing, Deprecation" gives a two-step lifecycle: "Deprecate feature" → "No new Models" / "Existing Models allowed"; then "Remove Feature" only when there are "No Model references".   - Limits: slide bullets only; no numbers on how many features were deprecated or how long removal takes; no statement that feature groups carry version numbers.

**DoorDash Fabricator:**

- Source: Kunal Shah (DoorDash), "Fabricator: End-to-End Declarative Feature Engineering Platform", QCon San Francisco talk (Oct 2022), InfoQ transcript page stamped 10 Oct 2023 — FULL-TEXT of transcript. On deprecation: "Typically, we don't allow our users to deprecate a feature." Reason: features are shared, and the platform must check whether other teams' production models use it. Process: "We do have deprecation processes, but they are manual." ### Inferences

- "New version, new name" is the industry default not because it is elegant but because the alternative (in-place change) silently changes inputs to a model that was fitted to the old values. Chronon's doc states this motive directly; Sculley et al. (section 3) gave the same reason in 2015.
- In most systems the "version" is only a suffix in a name. Lineage, deprecation and clean-up of old versions are then a separate, usually manual, job (DoorDash, Uber slides).
- First-class, numbered multi-version serving inside one feature view is new and immature in open source (Feast, 2026, SQLite-only) and absent in at least one large managed product (Vertex "only supports the version 0").

### Gaps

- No first-person statement from Uber, Airbnb, Stripe, LinkedIn, Netflix, Pinterest, Lyft, Twitter, Meta, Instacart, Monzo, Nubank, Capital One, PayPal or Block giving counts of concurrent feature versions or a written versioning policy. I could not open the Lyft, Pinterest, Twitter or Meta material; nothing found for Wayfair, Zillow, Robinhood, Nubank, Capital One, PayPal, Block.
- LinkedIn's internal Frame versioning rules: not found in a readable primary source.
- Date of the LinkedIn Feathr post should be re-verified against the page header.

## 2. Binding a model to its feature schema; serving two model versions with different feature versions at once

### Takeaway

The binding is done by making the feature list part of the model's own artifact or config: a Chronon Join, a Tecton Feature Service, a Hopsworks feature view version, a Databricks model "packaged with feature metadata", a Michelangelo model config, or a TensorFlow Transform graph inside the SavedModel. Because each model names its own feature set and the online store is keyed by (versioned) feature name, two models that need different feature versions can be served side by side; Uber's serving layer documents exactly this for shadow and A/B traffic.

### Cited Findings

- **Uber, 2017 — TOOL-EXTRACT.** A model configuration holds model type, hyper-parameters, data source reference and feature DSL expressions; the same DSL expressions are applied at training and prediction time. Each trained model is stored as a versioned object. More than one model can be deployed to one serving container; a model is addressed by UUID or tag; for A/B tests users deploy competing models and split traffic with Uber's experimentation framework from the client service. — [Uber blog, Meet Michelangelo](https://www.uber.com/blog/michelangelo-machine-learning-platform/)
  - Limits: 2017 description; tool extraction, wording not verified; does not show two models reading two versions of the *same* feature.
- **Uber, 2021 — TOOL-EXTRACT.** Joseph Wang, Yunfeng Bai, Jia Li, "Continuous Integration and Deployment for Machine Learning Online Serving and Models", 30 June 2021. "Auto-shadow" is built into the prediction service: traffic to a primary model is duplicated to a shadow model, and for the shadow model the service fetches from the online feature store only the features "not used in the primary model". Shadow models are treated as second class and can be paused under load. Unused models are auto-retired after an owner-set expiry, giving "a non-trivial reduction" in resources. Problems named: memory footprint and GC pauses as model count grows; a bad model can disrupt others in the same container. — [Uber blog, CI/CD for ML](https://www.uber.com/blog/continuous-integration-deployment-ml/)
  - Limits: tool extraction; no model counts; no explicit feature-schema compatibility check described; rollback not discussed in the extract.
- **Chronon — FULL-TEXT.** The Join is the per-model object: the docs' own example file is `joins/team_name/model.py` with the comment "all group_bys for the model for both backfill & serving"; the same Join is used "for online serving in your service" and to backfill training data. The online Fetcher is called with the join name and primary keys and "always assumes that you want the most up to date feature values". — [Chronon docs, Join](https://chronon.ai/authoring_features/Join.html)
  - Limits: nothing in the docs stores the join name inside a model artifact; the model-to-join link is by convention in the calling service.
- **Tecton (VENDOR) — FULL-TEXT.** "It is generally recommended that each model deployed in production have one associated Feature Service deployed, which serves features to the model." Variants of a Feature Service exist "to support A/B testing, staging, or incremental model development." — [Tecton docs, Feature Services](https://docs.tecton.ai/docs/reading-feature-data/feature-services)
- **Hopsworks (VENDOR) — FULL-TEXT.** "the feature view is a representation for a model in the feature store - the same feature view is used to retrieve feature vectors for operational model that was created with training data from this feature view." And: "A model deployment is also tightly coupled to the versioned feature views that supply its pre-computed features, so versioning the model alone is not enough." — [Hopsworks docs, Feature Views](https://docs.hopsworks.ai/latest/concepts/fs/feature_view/fv_overview/); [Hopsworks docs, Versioning](https://docs.hopsworks.ai/latest/concepts/fs/feature_group/versioning/)
- **Databricks (VENDOR) — FULL-TEXT.** A model must be logged with `FeatureEngineeringClient.log_model`; it is then "packaged with feature metadata" and "looks up features from feature tables at inference" automatically (batch `score_batch` or Model Serving). Warning in the docs: if you modify the training DataFrame after `load_df`, "the modifications are not applied when you use the model for inference. This decreases the performance of the model." Lineage from model to feature tables and functions is tracked in Unity Catalog. — [Databricks docs, Train models with feature store](https://docs.databricks.com/aws/en/machine-learning/feature-store/train-models-with-feature-store)
- **MLflow (open-source docs) — FULL-TEXT.** A model signature is validated automatically when a model is loaded as PyFunc or served via MLflow's REST API; required fields "Must be present or validation fails". Unity Catalog rejects models without signatures. — [MLflow docs, Model Signatures](https://mlflow.org/docs/latest/ml/model/signatures/)
  - Limits: a signature checks column names and types at the model boundary; it does not check that values were computed by the same feature definition.
- **TFX / TensorFlow Transform (Google docs) — FULL-TEXT.** "TensorFlow Transform builds transformations into the TensorFlow graph for your model so the same transformations are performed at training and inference time"; the transformations "become part of the TensorFlow graph. This approach helps avoid training/serving skew." The Transform component consumes the schema from SchemaGen and emits a SavedModel. — [TFX guide, Transform](https://www.tensorflow.org/tfx/guide/transform)
  - Limits: covers model-side transformations of raw inputs, not precomputed aggregates held in a feature store.
- **Feast, 2026 — FULL-TEXT.** The motivating case in ADR-0008 is exactly the reader's scenario: "model A uses v1 features, model B uses v2 features". Mechanism: version-qualified reference `driver_stats@v2:trips_today`; each version has its own online table (`project_driver_stats_v2`); `feast apply --no-promote` saves a version without making it active, "enabling phased rollouts"; pinning gives rollback. — [Feast ADR-0008](https://docs.feast.dev/project/adr/adr-0008-feature-view-versioning)
- Why a shared table with a version column was rejected (Feast blog): "a model trained against v1 of a feature must retrieve v1 rows, not v2 rows that happen to occupy the same table." — [Feast blog](https://feast.dev/blog/feature-view-versioning)

### Inferences

- The unit that makes side-by-side serving safe is "one model ↔ one named feature set". A feature flag or experiment then selects a *model*; the feature version follows from the model, never from the flag directly.
- Uber's shadow mechanism is the clearest first-person evidence that one online store serves two models with different feature lists on the same request; it is evidence of different feature *sets*, not explicitly of two versions of one feature.

### Gaps

- No first-person source showing a model artifact that embeds a hash of the feature definitions and refuses to serve on mismatch (Chronon's "semantic hash" is known from the code base but I did not find it in the docs pages read).
- No verified numbers on how many models/feature sets run concurrently at any named company.

## 3. Training-serving skew and consistency checks before a feature goes live

### Takeaway

The foundational Google sources say skew is common, costly and best prevented by logging at serving time and by versioned, validated schemas; modern feature platforms (Chronon, used by Airbnb and Stripe) turn this into an automatic job that compares logged online values with offline backfilled values and reports mismatch rates. None of the sources claims 100% consistency is achievable for streaming features.

### Cited Findings

- **Sculley et al. (Google), "Hidden Technical Debt in Machine Learning Systems", NIPS 2015, section "Data Dependencies Cost More than Code Dependencies", p. 3 — FULL-TEXT (PDF).** Exact passage requested: "One common mitigation strategy for unstable data dependencies is to create a versioned copy of a given signal." Next sentence: "it might be reasonable to create a frozen version of this mapping and use it until such a time as an updated version has been fully vetted." And the cost caveat: "Versioning carries its own costs, however, such as potential staleness and the cost to maintain multiple versions of the same signal over time." Why in-place improvement is dangerous: "even 'improvements' to input signals may have arbitrary detrimental effects in the consuming system"; a model fitted to a mis-calibrated signal means "a silent update that corrects the signal will have sudden ramifications for the model." The paper also notes this happens "when the engineering ownership of the input signal is separate from the engineering ownership of the model that consumes it." — [NeurIPS proceedings PDF](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
  - Limits: a position paper from experience; no measurements.
- **Martin Zinkevich (Google), "Rules of Machine Learning" — FULL-TEXT (web page, undated living document; first published c. 2016-2017).** "We have observed production machine learning systems at Google with training-serving skew that negatively impacts performance." Rule #29: save the features used at serving time and "pipe those features to a log to use them at training time"; "YouTube home page switched to logging features at serving time with significant quality improvements". Rule #31: "if you join data from a table at training and serving time, the data in the table may change"; snapshotting "still doesn't completely resolve the issue." Rule #37: "Measure Training/Serving Skew." Rule #10 (silent failures): "Sometimes you find tables that are months out of date, and a simple refresh improves performance more than any other launch that quarter!" Rule #11: "Give feature columns owners and documentation." — [Google Developers](https://developers.google.com/machine-learning/guides/rules-of-ml)
  - Limits: advice, not data; no numbers.
- **Baylor et al. (Google), "TFX: A TensorFlow-Based Production-Scale Machine Learning Platform", KDD 2017 — FULL-TEXT (PDF).** Data validation relies on "a schema that provides a versioned, succinct description of the expected properties of the data". Result at Google Play: comparing serving logs with training data found "a few features that were always missing from the logs, but always present in training"; an A/B experiment showed removing this skew "improved the app install rate on the main landing page of the app store by 2%." A model must be "safe to serve" before push; one failure seen was a model "trained using a newer version of a machine learning library than is used at serving time". — [TFX paper PDF (author copy)](https://stevenwhang.com/tfx_paper.pdf)
  - Limits: one product; the 2% figure is one experiment.
- **Breck, Polyzotis, Roy, Whang, Zinkevich (Google), "Data Validation for Machine Learning", SysML 2019 — FULL-TEXT (PDF).** Schema is stored in version control and co-evolves with data. Production sample: "more than 700 ML pipelines"; "The majority of cases have up to five schema revisions". Model unit tests (fuzzing training code with schema-conforming data): over 70% of pipelines had one; run "more than 80K times" in a month; "6% had failures". Case study (video recommendations migration): a backend stored features in a different format so they were "silently dropped"; "The total time to diagnose and fix the problem was two days, whereas similar issues have taken months to resolve." Skew is classified into feature skew, distribution skew and scoring/serving skew. — [MLSys 2019 PDF](https://mlsys.org/Conferences/2019/doc/2019/167.pdf)
  - Limits: Google-internal; validation detects, it does not version.
- **Chronon docs, "Online Offline Consistency" — FULL-TEXT.** Mechanism step by step: (1) the fetcher logs sampled inference requests and responses (keys, values, timestamp) to a `query_logs` table with 90-day retention; sampling is by key hash so all requests for a sampled key are captured; (2) a Spark job replaces the left side of the join with the logged table and recomputes the features offline; (3) it writes a `<join>_comparison` table; (4) metrics: mismatch rate `count(a != b) / count(*)`, missing, extra, and for numerics SMAPE and delta distribution. Honest limit stated up front: "While 100% consistency is desirable, it is not always possible." Causes: stream latency ("in the order of ms to seconds") and batch upload lag ("in the order of minutes or hours", centred on midnight). One DAG per join: `chronon_online_offline_comparison_{join_name}`; "logging must be enabled for this pipeline to work." — [Chronon docs, Online Offline Consistency](https://chronon.ai/test_deploy_serve/Online_Offline_Consistency.html); [Chronon docs, Orchestration](https://chronon.ai/setup/Orchestration.html)
  - Limits: design doc; no published thresholds or measured consistency rates from Airbnb.
- **Airbnb (Nikhil Simha), "Chronon – Airbnb's Feature Engineering Framework", Feature Store Summit 2022 slides — FULL-TEXT of slide text.** Consistency metrics listed: "Numerical: SMAPE", "Categorical: Inequality percentage", "Lists: Edit Distance". Online serving target "Low latency ~10ms, high QPS". — [Airbnb FS Summit 2022 slides (PDF)](https://content.hopsworks.ai/hubfs/Feature%20Store%20Summit%202022/FS%20Summit%2022%20-%20Airbnb.pdf)
- **Stripe (Ben Mears), "Shepherd: How Stripe adapted Chronon to scale ML feature development", 15 April 2024 — FULL-TEXT.** Stripe chose Chronon partly for "built-in consistency monitoring". For its first model (SEPA fraud, "over 200 features", batch and streaming) Stripe "built monitoring and alerting for Shepherd—including integrating with Chronon's online offline consistency monitoring" and added "support for modeling delay in the offline training data" to avoid skew. Scale: "training data can include thousands of features and billions of rows"; p99 feature freshness of 150ms after moving streaming to Flink; the model "blocks tens of millions of dollars of additional fraud a year." — [Stripe blog](https://stripe.com/blog/shepherd-how-stripe-adapted-chronon-to-scale-ml-feature-development)
  - Limits: author name from memory of the byline (verify); no consistency percentages; no description of how a feature definition change was rolled out. The SEPA model was launched as a new Shepherd-only model rather than migrated feature by feature.
- **Netflix (Vivek Kaushal et al.), "Evolution of ML Fact Store", Netflix Tech Blog, 26 April 2022 — FULL-TEXT via a syndicated mirror (noise.getoto.net; the original on Medium was blocked).** Netflix avoids skew differently: it logs raw *facts*, and "Feature encoders are shared between compute applications and offline feature generators." "Temporal accuracy... is the ability to regenerate the exact set of features that were generated for the recommendations." Monitoring deployed "more than two years ago" caught "more than 95% of data issues early". — [Mirror of Netflix Tech Blog post](https://noise.getoto.net/2022/04/26/evolution-of-ml-fact-store/) (original: <https://netflixtechblog.com/evolution-of-ml-fact-store-5941d3231762>)
  - Limits: mirror text, not the original page; personalization models only.
- **TFX Data Validation docs — FULL-TEXT.** ExampleValidator supports "Training-Serving Skew Detection" by "comparing examples in training and serving data" and drift detection across a series of data. — [TFX guide, TFDV](https://www.tensorflow.org/tfx/guide/tfdv)

### Inferences

- The consistency job is the feature-store equivalent of a dark launch: the new feature version is computed and served (and logged) with no model depending on it, and it is promoted only when measured mismatch is acceptable. Chronon's docs describe the measurement; they do not describe a formal promotion gate.
- Two families of design exist: "backfill and verify against logs" (Chronon, Tecton) and "log facts, regenerate features with shared code" (Netflix, Google Rule #29). The second makes definition changes cheap offline but still needs the new encoder deployed online.

### Gaps

- No published consistency thresholds or measured mismatch rates from Airbnb, Stripe, Uber or DoorDash.
- Uber "feature quality" posts and DoorDash consistency posts could not be opened.

## 4. Point-in-time correctness and backfill: recomputing history, populating the online store before use, retention

### Takeaway

A changed feature needs history recomputed before any model can be trained on it, and the first-person numbers show why platforms invest in backfill: waiting for logs takes "several weeks" (Netflix) versus "hours" for regeneration. Backfill is the costly step that a new version always incurs; several vendors state plainly that it "incurs cost and downtime" if done in place, and retention of old versions is mostly manual.

### Cited Findings

- **Netflix, 2022 — FULL-TEXT (mirror).** "Our machine learning models train on several weeks of data." Logging a new encoder's output means waiting "several weeks for the data collection"; "Regeneration takes hours compared to weeks taken by the feature logging." The offline feature generator supports "new, existing, or updated feature encoders." Lessons: "Pay the storage, network, and compute cost" first and optimise later; lack of scalability testing caused "issues that took us weeks to clean up." — [Mirror of Netflix Tech Blog post](https://noise.getoto.net/2022/04/26/evolution-of-ml-fact-store/)
- **Airbnb, 2022 slides — FULL-TEXT.** Goal slide "Log & Wait vs Backfill": "Large training data ranges -> lot of waiting"; "New features need to be derived from existing raw data". Offline jobs are idempotent with "Auto backfill": "Job always tries to fill in all of its unfilled range". — [Airbnb FS Summit 2022 slides (PDF)](https://content.hopsworks.ai/hubfs/Feature%20Store%20Summit%202022/FS%20Summit%2022%20-%20Airbnb.pdf)
- **Airbnb Zipline, Strata NY 2018 slides — FULL-TEXT of slide text.** Motivation quotes on slides: "I spend 60% of my time generating training data" and "My backfill is running." — [Strata 2018 slides (PDF)](https://conferences.oreilly.com/strata/strata-ny-2018/cdn.oreillystatic.com/en/assets/1/event/278/Zipline_%20Airbnb_s%20data%20management%20platform%20for%20machine%20learning%20Presentation.pdf)
  - Limits: slide text only; unattributed user quotes.
- **Chronon docs — FULL-TEXT.** Point-in-time rule: with temporal accuracy, a 10-day window for a row stamped 2023-12-20 12:01:01.923 includes only events from 2023-12-10 12:01:01.923 to one millisecond before the row. Batch-sourced features default to "midnight accurate". Reuse to cut backfill cost: "Chronon will try as much as possible to avoid unnecessary backfills across runs"; the Bootstrap feature lets a training table "utilize logging for production features and backfill for experimental features", and with `bootstrap_from_log`, "for features that are already logged, Chronon will run the bootstrap to pull values from logs and skip backfill." Orchestration: one DAG per join "performs backfill and daily frontfill". — [Chronon docs, Join](https://chronon.ai/authoring_features/Join.html); [Chronon docs, Bootstrap](https://chronon.ai/authoring_features/Bootstrap.html); [Chronon docs, Orchestration](https://chronon.ai/setup/Orchestration.html)
  - Limits: no backfill durations or costs given.
- **Uber, 2017 — TOOL-EXTRACT.** Batch features are precomputed and bulk-loaded from HDFS into Cassandra; for near-real-time features Uber provides a tool to backfill and generate training data from historical logs. — [Uber blog](https://www.uber.com/blog/michelangelo-machine-learning-platform/)
- **Uber, 2022 slides — FULL-TEXT.** Architecture slide labels a "Backfill Pipeline (bootstrap only)". — [Uber FS Summit 2022 slides (PDF)](https://content.hopsworks.ai/hubfs/Feature%20Store%20Summit%202022/FS%20Summit%2022%20-%20Uber.pdf)
- **DoorDash (Kunal Shah), QCon SF 2022 transcript — FULL-TEXT.** Before Fabricator: about 400 unique production features, about 100 billion daily feature uploads, about 60 jobs. A year later: "over 2000 unique features", "about a trillion values on a daily basis" into offline storage, "about 500 different jobs". Iteration went "from days to hours". Backfill: a "launch backfill" button; pick "the last 30 days" of partitions and "within a few minutes" jobs are launched in parallel; before, "backfill was a reasonably involved task" needing edits to production ETL. Embedding features previously ran "about 10 to 12 hours every day", so "One change would take them each day to propagate"; later "more than 10x speedup". Online: a new offline partition triggers the upload service into Redis automatically. — [InfoQ transcript](https://www.infoq.com/presentations/fabricator-ml)
  - Limits: talk; QCon abstract gives different volumes ("over 500 unique features and 10B feature values", [QCon abstract](https://qconsf.com/presentation/oct2022/fabricator-end-end-declarative-feature-engineering-platform)) — the abstract appears to describe the earlier state; the discrepancy is not explained. "Within a few minutes" is launch time, not completion time.
- **Tecton (VENDOR) — FULL-TEXT.** In-place change of a materialised view "re-runs the backfill process from the feature start time" and the view is unavailable online meanwhile; hence the variant (`:v2`) practice, which materialises the new version alongside. — [Tecton docs, Suppress Recreates](https://docs.tecton.ai/docs/manage-costs/suppress-recreates); [Tecton docs, prevent_destroy](https://docs.tecton.ai/docs/running-in-production/prevent_destroy)
- **Feast, 2026 — FULL-TEXT.** "Each version requires its own materialization" (`feast materialize --views driver_stats --version v2 <start> <end>`); design is "more operationally complex — more tables to manage, more materialization jobs to schedule". — [Feast blog](https://feast.dev/blog/feature-view-versioning)
- **Hopsworks (VENDOR) — FULL-TEXT.** Version bump is followed by "backfill the new feature group". Data versioning (time travel) is separate: read "as-of ingestion time" for reproducible training data or "as-of event time" for point-in-time-correct data. — [Hopsworks docs, Versioning](https://docs.hopsworks.ai/latest/concepts/fs/feature_group/versioning/)
- **Retention of old versions.** DoorDash: usage must be zero "for like 30 days in production" before manual bulk clean-up ([InfoQ transcript](https://www.infoq.com/presentations/fabricator-ml)). Uber: removal only when "No Model references" ([Uber slides](https://content.hopsworks.ai/hubfs/Feature%20Store%20Summit%202022/FS%20Summit%2022%20-%20Uber.pdf)); unused *models* auto-retire after an owner-set expiry ([Uber CI/CD post](https://www.uber.com/blog/continuous-integration-deployment-ml/), TOOL-EXTRACT). Feast: "No mechanism to prune old versions" ([Feast ADR-0008](https://docs.feast.dev/project/adr/adr-0008-feature-view-versioning)). Chronon's query log table sets `'retention' = '90'` ([Chronon docs](https://chronon.ai/test_deploy_serve/Online_Offline_Consistency.html)).
- **Pinterest — SNIPPET only.** A Pinterest Engineering post "How Pinterest Accelerates ML Feature Iterations via Effective Backfill" is summarised by third parties as describing forward logging's calendar-time cost and a two-stage "Feature Staging" then "Feature Promotion" backfill, with "up to 90x" cost/iteration-time reduction. I could not open the original. — [third-party digest](https://thenote.app/post/en/how-pinterest-accelerates-ml-feature-iterations-via-effective-backfill-ykhzxukvad)
  - Limits: unverified; do not quote.

### Inferences

- The practical sequence for a v2 feature is: define v2 → offline backfill (hours with a backfill engine; weeks if you must log and wait) → turn on online materialisation/streaming for v2 with no reader ("dark write") → compare logged online values with offline values → train model B on v2 history → shadow/A-B model B against model A → retire v1 when no model references it. Each step is documented by at least one source above, but no single source narrates the whole sequence end to end for one real feature.
- "How long old versions are kept" is governed by model references, not by a time policy: the old feature lives as long as any deployed model (including the rollback target) names it.

### Gaps

- No first-person dollar or compute-hour cost for backfilling a changed feature, and no first-person duration for a full-history backfill of a long-window streaming aggregate.
- No explicit first-person description of "shadow materialisation" of a v2 feature in the online store before a model uses it, other than as implied by Chronon's online toggle plus consistency job and Tecton's variants.
- Netflix DeLorean (2016) and the Airbnb 2024 open-source announcement could not be opened; their often-cited claims are not recorded here.

## 5. Propagating an upstream schema change through the chain (parallel v2 tables and v2 features), lineage, deprecation

### Takeaway

I found no first-person account that walks a raw-table change through a chain of intermediate tables into features by publishing a full parallel v2 chain. What the sources do establish is each ingredient separately: the 2015 recommendation to version a signal, per-feature `_v2` conventions, cascading "destructive change" rules, feature-to-model lineage used to gate deprecation, and one Uber migration that ran old and new metadata side by side behind a kill switch.

### Cited Findings

- **Sculley et al. 2015 — FULL-TEXT.** The versioned-copy recommendation (quoted in section 3) is the earliest statement of the parallel-version pattern. The same paper asks for "Static Analysis of Data Dependencies", calling such tools "essential for error checking, tracking down consumers, and enforcing migration". — [NeurIPS proceedings PDF](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)
- **Tecton (VENDOR) — FULL-TEXT.** A schema change in a *Data Source* cannot be suppressed and forces recreation of dependent Feature Views: recreates cannot be suppressed on "Modification of the schema ... of a Data Source or Feature View", and "destructive changes cascade to dependent objects". An "Upstream Data Source migration" that keeps the same output schema is the one upstream change that may be applied in place. — [Tecton docs, Suppress Recreates](https://docs.tecton.ai/docs/manage-costs/suppress-recreates); [Tecton docs, prevent_destroy](https://docs.tecton.ai/docs/running-in-production/prevent_destroy)
  - Limits: applies inside Tecton's object graph only; tables upstream of the registered data source are outside its view.
- **Chronon — FULL-TEXT.** Intermediate ETL is expressed as versioned `StagingQuery` objects (example: `driver_table.v1`) that Joins reference by name, so an upstream change can be expressed as a new StagingQuery version feeding a new GroupBy/Join version. — [Chronon docs, Bootstrap](https://chronon.ai/authoring_features/Bootstrap.html)
  - Limits: this is what the API permits; the docs do not narrate such a migration.
- **Uber (Paarth Chothani, Dehua Lai, Nicholas Marcott), "Palette Meta Store Journey", 18 January 2024 — TOOL-EXTRACT.** Failure: a major incident in 2021 was attributed to inadequate schema validation on Palette metadata; validation ran client-side, so users who had not rebased skipped the newest checks; a bad metadata change reached master and affected online serving; resolution took several hours. A change to one feature group caused updates for all "hundreds" of feature groups because there was no incremental update, which prolonged rollbacks; metadata updates took over an hour to propagate. Remedy: server-side validation before registration; incremental updates (end-to-end propagation to offline and online systems in about 15 minutes instead of over an hour). Migration method: both old and new metadata versions were made available to online serving behind a common wrapper, with a kill switch choosing which version serving used, and comparison metrics/logs across generation and offline serving to show equivalence. The rearchitecture took more than a year. — [Uber blog](https://www.uber.com/blog/palette-meta-store-journey/)
  - Limits: tool extraction, wording not verified. The side-by-side-plus-kill-switch migration was of the *metadata system*, not of a feature's data schema. The post does not describe feature versioning.
- **Lineage.** Uber: "Feature -> Model Lineage via metadata" gates deprecation ([Uber slides](https://content.hopsworks.ai/hubfs/Feature%20Store%20Summit%202022/FS%20Summit%2022%20-%20Uber.pdf), FULL-TEXT). Databricks (VENDOR): tables and functions used to create a model "are automatically tracked and displayed" ([Databricks docs](https://docs.databricks.com/aws/en/machine-learning/feature-store/train-models-with-feature-store), FULL-TEXT). Feathr: registry UI tracks "project and feature level lineage data" on Azure Purview or SQL ([Feathr registry doc](https://raw.githubusercontent.com/feathr-ai/feathr/main/docs/concepts/feature-registry.md), FULL-TEXT). Hopsworks exposes `explicit_provenance` APIs for feature store and model registry (page titles seen in the docs sitemap; content not read).
  - Limits: all of these are feature↔model or feature↔registered-source lineage. None is shown tracing a feature back through ten warehouse tables to a source column.
- **Google, Breck et al. 2019 — FULL-TEXT.** When data and schema disagree the user either fixes the data generation or updates the versioned schema; this happened in most of 700+ pipelines, usually up to five times. — [MLSys 2019 PDF](https://mlsys.org/Conferences/2019/doc/2019/167.pdf)
- **DoorDash — FULL-TEXT (transcript).** Registry changes are deployed by CD; downstream systems "take actions based on changes to the registry" automatically. — [InfoQ transcript](https://www.infoq.com/presentations/fabricator-ml)

### Inferences

- For the reader's "ten downstream tables" case, feature platforms only version the last hop (source → feature → feature set → model). The warehouse hops before the registered source are governed by warehouse practice (versioned tables/views, contracts), which other researchers' notes should cover; the feature store's contribution is that the v2 chain can terminate in `feature_v2` and be consumed only by model B.
- Tecton's rule that an upstream migration with an unchanged output schema may be applied in place, while any schema change forces a new/rebuilt feature, is the cleanest written statement of where the "contract" boundary sits.

### Gaps

- No first-person, step-by-step account of a parallel v2 table chain feeding v2 features at any named organisation. This is a real gap in the public record, not just in my search.
- OpenLineage integration with feature stores: not researched to a primary source.
- Hopsworks provenance and Vertex lineage page contents not read.

## 6. Limits and failures

### Takeaway

The approach works but is costly and partly manual: every version means another backfill, another online table and another pipeline to keep fresh; clean-up of old versions is manual or missing; consistency is never perfect for streaming features; and first-person postmortems of a feature change silently degrading a model are rare in public (Google's Play skew and Uber's 2021 metadata incident are the two I could document).

### Cited Findings

- **Cost is acknowledged at the origin.** "Versioning carries its own costs, however, such as potential staleness and the cost to maintain multiple versions of the same signal over time." — [Sculley et al. 2015](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf) (FULL-TEXT)
- **Duplicate pipelines and storage.** Feast's per-version tables are "more operationally complex — more tables to manage, more materialization jobs to schedule" ([Feast blog](https://feast.dev/blog/feature-view-versioning)); "No version pruning mechanism may lead to unbounded growth" ([Feast ADR-0008](https://docs.feast.dev/project/adr/adr-0008-feature-view-versioning)). Tecton files rematerialisation under cost optimisation: it "incurs cost and downtime" ([Tecton docs](https://docs.tecton.ai/docs/manage-costs/suppress-recreates)). Stripe split its KV store into a cheap write-once store and a costlier memcache-based store specifically to control serving cost ([Stripe blog](https://stripe.com/blog/shepherd-how-stripe-adapted-chronon-to-scale-ml-feature-development)). All FULL-TEXT.
- **Immaturity in open source.** Feast multi-version serving (2026): "Version-qualified reads are only on SQLite initially"; "Offline store versioning is out of scope"; "Cross-version joins in get_historical_features are not supported"; and "Offline versioning is not supported, creating a gap for reproducing historical training data." The blog says getting versioning right "is surprisingly hard, especially for materialization." — [Feast ADR-0008](https://docs.feast.dev/project/adr/adr-0008-feature-view-versioning); [Feast blog](https://feast.dev/blog/feature-view-versioning) (FULL-TEXT)
- **Managed products without versions.** Vertex: "only supports the version 0 for features" ([Google Cloud docs](https://cloud.google.com/vertex-ai/docs/featurestore/latest/overview)); SageMaker: features can be added but "you cannot remove those features" ([AWS docs](https://docs.aws.amazon.com/sagemaker/latest/dg/feature-store-update-feature-group.html)). FULL-TEXT, VENDOR.
- **Features that cannot be versioned cheaply — streaming aggregates.** Tecton will not apply in place "Some modifications of a Spark Stream Feature View with window aggregates, where the modification would invalidate the checkpoint" ([Tecton docs](https://docs.tecton.ai/docs/manage-costs/suppress-recreates), FULL-TEXT, VENDOR). Chronon: stream and batch upload lag mean "100% consistency ... is not always possible" ([Chronon docs](https://chronon.ai/test_deploy_serve/Online_Offline_Consistency.html), FULL-TEXT). Stripe had to change Chronon's storage of streaming events to pre-aggregated "tiles" to meet latency ([Stripe blog](https://stripe.com/blog/shepherd-how-stripe-adapted-chronon-to-scale-ml-feature-development), FULL-TEXT).
- **Features that cannot be versioned cheaply — embeddings.** Hopsworks singles out a changed embedding algorithm as a breaking change requiring a new version and backfill ([Hopsworks docs](https://docs.hopsworks.ai/latest/concepts/fs/feature_group/versioning/), FULL-TEXT, VENDOR). DoorDash: embedding pipelines ran "about 10 to 12 hours every day" before optimisation ([InfoQ transcript](https://www.infoq.com/presentations/fabricator-ml), FULL-TEXT). Orr, Sanyal, Ling, Goel, Leszczynski (Stanford, Uber AI, Apple), "Managing ML Pipelines: Feature Stores and the Coming Wave of Embedding Ecosystems", VLDB 2021 tutorial, arXiv 2108.05053 (11 Aug 2021): "As embeddings get retrained and updated, just like features, the downstream models can become stale and out-of-date"; "Any inherent embedding quality issue will impact all downstream models using those embeddings"; "Unlike features, standard tabular metrics are inadequate for embeddings." ([arXiv PDF](https://arxiv.org/pdf/2108.05053), FULL-TEXT).
  - Limits: tutorial abstract-level claims; no cost figures.
- **Freshness versus cost.** Wooders et al., "RALF: Accuracy-Aware Scheduling for Feature Store Maintenance", PVLDB 17 (2024): frames keeping features fresh as costly and proposes "feature store regret" to prioritise "expensive feature updates" ([PVLDB PDF](https://www.vldb.org/pvldb/vol17/p563-wooders.pdf), FULL-TEXT of the opening pages only — title and details beyond the abstract not checked carefully; verify before citing specifics).
- **Silent degradation, first-party.** Google Play: features "always missing from the logs, but always present in training"; fixing it gave +2% app installs ([TFX paper](https://stevenwhang.com/tfx_paper.pdf)). Google video recommendations: features "silently dropped", two days to fix with validation "whereas similar issues have taken months" ([Breck et al.](https://mlsys.org/Conferences/2019/doc/2019/167.pdf)). Google generally: tables "months out of date" ([Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml)). All FULL-TEXT.
- **Incident, first-party.** Uber 2021 Palette metadata incident: bad metadata change, Tier-1 online serving affected, hours to resolve, rollbacks prolonged because one change touched hundreds of feature groups ([Uber blog](https://www.uber.com/blog/palette-meta-store-journey/), TOOL-EXTRACT; "Tier-1" wording from SNIPPET).
- **Shared serving risk when many model versions coexist.** Uber: growing model counts raise memory and GC pauses; "a bad model" can disrupt others in the same container; shadow models are paused under load ([Uber CI/CD post](https://www.uber.com/blog/continuous-integration-deployment-ml/), TOOL-EXTRACT).
- **Organisational limits (feature owners versus model owners).** Sculley: danger arises when signal ownership "is separate from the engineering ownership of the model that consumes it" ([paper](https://papers.nips.cc/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf)). Rules of ML #11: give feature columns owners ([page](https://developers.google.com/machine-learning/guides/rules-of-ml)). DoorDash: users may not deprecate features themselves because "a feature may be shared across multiple users"; "There is a process but it's not a trivial one" ([InfoQ transcript](https://www.infoq.com/presentations/fabricator-ml)). Uber: validation that depended on each user rebasing failed; moved server-side ([Uber blog](https://www.uber.com/blog/palette-meta-store-journey/), TOOL-EXTRACT).
- **Design regret.** DoorDash's speaker says the offline-serving API had "insufficiencies around how we treat the concept of time" that were added later ([InfoQ transcript](https://www.infoq.com/presentations/fabricator-ml), FULL-TEXT). Netflix: early storage optimisation made query performance hard; advice is to "Pay the storage, network, and compute cost" first ([mirror](https://noise.getoto.net/2022/04/26/evolution-of-ml-fact-store/), FULL-TEXT of mirror).

### Inferences

- The approach "stops working" economically where a version's backfill or steady-state compute is large relative to the experiment's value: long-window streaming aggregates (checkpoint/state must be rebuilt), embeddings (recompute for every entity, and v1/v2 vectors cannot be mixed), and widely shared features (many downstream models must each be retrained and re-validated before v1 can be removed).
- The scarcity of public postmortems means the article should not claim that versioned features have been shown to prevent incidents at a measured rate; the evidence is mechanism plus a handful of anecdotes.
- Old versions tend to accumulate: every source that discusses removal describes it as manual, reference-gated or absent.

### Gaps

- No first-person figure for the storage or compute overhead of running v1 and v2 feature pipelines in parallel.
- No public first-person postmortem (outside Google's papers and Uber's metadata incident) of an in-place feature definition change degrading a production model. Third-party blog anecdotes exist (search snippets) but are not from named implementers and are excluded.
- Not covered for lack of readable primary sources: Twitter, Meta (FBLearner Feature Store / F3), Pinterest Galaxy, Lyft, Spotify Jukebox, Instacart, Monzo, Wayfair, Zillow, Robinhood, Nubank, Capital One, PayPal, Block. Monzo and Lyft appeared only in third-party digests (SNIPPET) and are not used.
- All Uber blog quotations need re-verification against the raw pages (TOOL-EXTRACT).
